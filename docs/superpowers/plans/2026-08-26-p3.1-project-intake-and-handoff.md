# P3.1 — Project Intake & Employee Handoff — Implementation Plan

Companion to `docs/production-build/P3.1-DESIGN.md`. **Do not execute any
task below until both documents are owner-approved.** Follows the same
subagent-driven-development process used for P3: fresh implementer per
task, independent reviewer per task, fix-loop rounds, ledger file at
`.superpowers/sdd/2026-08-26-p3.1-project-intake-and-handoff/progress.md`.

Schema migration numbering: next available is `schema/018` (016/017 are
P3's). One cohesive migration for all schema changes below, mirroring how
016 bundled its related changes — not split across multiple numbered files.

---

## Task 1 — Schema migration (schema/018)

- `project_number_counters` table + `generate_project_number(org_id)`
  helper (design §1) — **enable RLS with no policies and revoke direct
  grants from `authenticated`/`anon`**, matching the `audit_financial_tables`
  precedent (schema/016) for a SECURITY-DEFINER-only-access table. An
  earlier draft of the design omitted this; it's now explicit in §1 and
  must not be dropped again here.
- `projects.pricing_model` → nullable. `projects.pricing_model_label` is
  **kept as-is** (an earlier draft of this plan incorrectly had it dropped
  — it's actively read by `ProjectListWorkspace.tsx`,
  `supabaseFinancialRepository.ts`, and `AdminOverviewScreen.tsx`/
  `AdminFinancialsScreen.tsx`; no migration touches this column at all).
- `projects.phase` → converted from `text` to new `project_phase` enum
  (design §5) — confirm zero non-null existing values before the type
  change (expected, since no live code *writes* it today; verify, don't
  assume). `phase` **is** read today by `supabaseFinancialRepository.ts`
  and rendered raw by `AdminFinancialsScreen.tsx` (`{projectMeta.phase}
  phase`) — the type change itself doesn't break that select, but once
  this package starts writing real enum values, revisit that render to
  humanize the slug (e.g. `contract_pending` → "Contract Pending") instead
  of showing it raw. Not a blocking change for this task, but don't lose
  track of it — add a small follow-up note to Task 9 or wherever the UI
  work naturally touches that screen.
- `project_clients`: new enums (`contact_role`, `contact_method`,
  `contact_info_status`) + new columns (design §4). An audit trigger
  already exists on this table (`schema/012`) — no new trigger needed, only
  the new columns.
- New `project_briefs` table + RLS (`project_briefs_staff_full`) + the
  **existing, reused** `log_audit_project_settings()` trigger (design §5 —
  not `log_audit()`, which would crash on a `project_id`-keyed table with
  no `id` column; this function already exists in schema/012 for exactly
  this case).
- New `project_site_info` table (+ new `intake_item_status` enum) + RLS
  (`project_site_info_staff_full`) + the same reused
  `log_audit_project_settings()` trigger (design §6). No
  `designer_contact_*` columns — engineer/designer/architect contacts go
  through `project_clients` with `role='professional_contact'` (Task 6),
  not a second contact surface here.
- `project_staff_assignments`: new enums (`staff_request_type`,
  `handoff_priority`) + new nullable columns (design §8) — no new RLS
  policy (inherits existing admin-only policy).
- Revise `create_project_with_defaults()`: remove `p_project_number`
  param, call `generate_project_number()` internally; make
  `p_pricing_model`/`p_fee_basis`/`p_fee_basis_points`/
  `p_fee_fixed_amount_cents` optional with conditional `project_fee_rules`
  insert (design §2). `p_pricing_model_label` stays as-is (nullable
  pass-through, unaffected — the column isn't being dropped).
- New `set_project_fee_terms()` RPC — admin-only (pending decision 5),
  atomically upserts `project_fee_rules`, updates `projects.pricing_model`,
  and optionally updates `projects.pricing_model_label` in the same call
  (design §2) — the label and the terms it describes are set together.
- Down migration, `supabase/migrations/` mirror (byte-identical — the
  existing `checkMigrationMirrorsByteIdentical()` CI guard will catch
  drift), and new SQL tests covering:
  - concurrent `create_project_with_defaults()` calls for the same org
    produce distinct sequential numbers (the atomicity claim in design §1
    — do not just assert the happy path, actually exercise concurrent
    calls or simulate the row-lock behavior)
  - numbering resets/continues correctly across a year boundary is
    **not** testable within one run (no way to fake `now()`) — instead
    unit-test `generate_project_number()`'s year-scoping logic against two
    manually-seeded counter rows for the same org, different years
  - a project created with no pricing model at all succeeds and has zero
    `project_fee_rules` rows
  - `set_project_fee_terms()` rejects a non-admin caller
  - existing (pre-migration) `project_number` values are unchanged and a
    newly generated number never collides with one (seed a fixture with a
    legacy-format number first)
  - `project_briefs`/`project_site_info` RLS: a staff session without a
    project assignment (where required) cannot read/write another org's
    rows; a client session gets zero rows from either table
  - `internal_notes` is never selectable by a client-role session (service-
    layer test, not just RLS — per design §5's note that column-level
    hiding is enforced by the repository read, not RLS alone)

**Reviewer focus:** concurrency correctness of the numbering upsert,
whether the admin-only checks on the two RPCs are enforced at the RLS layer
too (not just inside the function body — this is exactly the class of bug
P3's own round-2 review found on `projects_staff_update`), and whether the
migration is safe to run against the live database with existing project
rows present (no locking/rewrite of the whole `projects` table if avoidable).

## Task 2 — Service layer

- Revise `packages/02-app-shell/src/services/projectService.ts`:
  `createProject()`'s param shape drops project number and makes pricing
  fields fully optional; add `setProjectFeeTerms()`.
- New service functions (new file or extend `projectService.ts` — decide at
  implementation time based on file size): `upsertProjectBrief()`,
  `upsertProjectSiteInfo()`, `upsertProjectContact()`,
  `listProjectContacts()`, `updateStaffAssignmentHandoff()`.
- Repository read functions for: project brief, site info, contacts list,
  and the derived checklist-status computation (design §9 — status is
  computed here, not stored).
- Every function follows the existing repository-read / plain-service-
  write pattern (design §10) — no logic in Server Actions or components.

**Reviewer focus:** does checklist-status derivation actually match design
§9's table exactly (each item's stated data source); does the client-facing
repository read omit `internal_notes` unconditionally (not just when a flag
happens to be false).

## Task 3 — Server Actions

Thin wrappers only, one per new service function, matching the existing
`createAction.ts`/`statusAction.ts` pattern (parse input, call service,
shape result — no logic).

## Task 4 — Revise the create-project panel

`ProjectListWorkspace.tsx`: remove the project-number input and "Suggest
next number" button (and delete `suggestNextProjectNumber()` entirely, not
just its call site); remove every pricing field; reduce the required-field
set to design §3's list; add the inline contact quick-add for the primary
homeowner; add the "address not established" toggle. Confirm the
post-create redirect to `/admin/projects/[id]/setup` still fires (it
already does today — don't regress it).

**Reviewer focus:** does the removed pricing-model guard in
`createProject()` (the defense-in-depth fix from P3's own round 2) still
have an equivalent check now that pricing is optional — i.e., if a
pricing model IS supplied, is it still restricted to the two fee-supported
values; is there any leftover dead code referencing the deleted
suggestion helper or the removed `p_project_number` RPC parameter.

## Task 5 — Project Brief screens (Concept & Scope, Property & Site Info)

New component(s) under `packages/02-app-shell/src/components/` rendering
the `project_briefs`/`project_site_info` forms per design §§5–6, with the
`intake_item_status` selector shown only on the fields that use it. Route(s)
under `apps/web/app/admin/projects/[id]/brief/` (or nested tabs — decide at
implementation time). Respect the archived-project guard already
established for the team/setup routes (render `NoProjectAccess` for an
archived project before any write-capable form renders).

## Task 6 — Contacts management UI

New section/component for `project_clients` (list + add/edit), used both
inline in the create panel (Task 4) and on its own Setup-checklist-linked
page. One form, two entry points — do not build two separate contact forms.
This is also the single surface for engineer/designer/architect contacts
(`role='professional_contact'`, design §4) — Task 5's site-info form does
not get its own contact fields; if it needs to reference "who's the
designer," it links to this list rather than duplicating entry.

## Task 7 — Revise `ProjectSetupChecklist.tsx`

Extend to the 11-item list in design §9, with real per-item derived status
(Not started / In progress / Complete) computed via Task 2's repository
functions — replace the current two-item hardcoded structure, not append
to it. Route "Preliminary estimating" to the existing `/admin/estimate`
screen (confirm the real route path at implementation time — do not invent
a new one). Route "Contract & pricing terms" to Task 8's new screen.

**Reviewer focus:** does every "Coming later" item stay genuinely inert
(`aria-disabled`, no href/onClick — matches the existing pattern already
used for the six current placeholder items); does every "Real" item's
derived status actually update after data changes (test by writing a row
then re-fetching, not just checking the query shape).

## Task 8 — Contract & Pricing Terms screen

New minimal screen calling `setProjectFeeTerms()` — admin-only per decision
5, gated the same way the create panel already is. Shows current
`pricing_model`/fee terms/`pricing_model_label` if set, "Not yet
determined" if not — this is the field's new home, moved out of Task 4's
create panel, not a new field.

## Task 9 — Staff handoff UI

Extend the existing team page (`ProjectTeamWorkspace.tsx` /
`apps/web/app/admin/projects/[id]/team/page.tsx`) with the new
`project_staff_assignments` handoff fields, editable inline per assignment
row. Add the compact "Your assignment" card to `AdminOverviewScreen.tsx`
for a session with an active assignment on the current project, including
`project_briefs.summary` and `staff_function` alongside the assignment's
own fields (design §8 — both are on the owner's explicit list, don't just
show the assignment columns). While touching this screen, humanize
`projectMeta.phase`'s rendering (Task 1's note) instead of leaving it as
the raw enum slug once real values start being written.

## Task 10 — Regression coverage

- Route-smoke coverage for every new route (matching the existing pattern
  from P3 Task 6, extended, not duplicated).
- Unit tests for the checklist-status derivation logic (Task 2) covering
  every one of the 11 items' real/coming-later split.
- A live checkpoint script extension (`scripts/db/live-p3-checkpoint.mjs`
  or a new sibling `live-p3.1-checkpoint.mjs` — decide at implementation
  time) exercising: create a project with no pricing model, add a contact,
  fill in a brief, set fee terms later, confirm the checklist reflects
  each change.

## Task 11 — Documentation

Apply design §12's updates to `PRODUCTION-ROADMAP.md` and
`PRODUCT-COMPLETENESS-MATRIX.md` exactly as scoped there — targeted edits,
not a rewrite. No change to `PRODUCT-VISION.md` beyond an optional
footnote pointing at `P3.1-DESIGN.md`.

## Final whole-branch review

One fix dispatch + one scoped re-review only (no second fix wave), per the
established convention — covering cross-task consistency (e.g., does the
Task 7 checklist's "Contract & pricing terms" status genuinely reflect
Task 8's writes; does Task 4's quick-add contact form produce identical
rows to Task 6's full form) rather than re-reviewing each task in
isolation again.
