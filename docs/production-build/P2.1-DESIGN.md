# Package P2.1 — Financial Master Data & Project Setup — Design Record

**Status: Complete.** Approved 2026-07-28 as a scoped follow-on to
`docs/production-build/WORKBOOK-GAP-ANALYSIS.md` (the approved gap
analysis), inserted into `PRODUCTION-ROADMAP.md` between P1 (complete)
and P4 (Estimating & Budgeting UI + QuickBooks Import) — P4 needs this
package's cost-code granularity to exist before real budget-ledger
entry UI can be built against it.

**Source of truth:** `docs/reference/Stone_Column_Cost_Plus_Blank_Template.xlsx`
(tracked in git as of this package). Every division name, cost code,
activity name, and Include-in-Estimate?/Billable Cost? flag in this
package's seed data is transcribed **verbatim** from that workbook's
`BUDGET` sheet — generated programmatically from a parsed read of the
file (not hand-typed), to eliminate transcription risk across 113 rows.
Row/division counts were cross-checked twice: once against the `BUDGET`
sheet directly, once against the `INVOICE DETAIL` sheet (which lists
the same 113 codes independently) — both parses agree exactly.

## Exact scope

Financial master data and project setup only, per explicit instruction:

- Normalized `divisions` (per-project) and 113 workbook cost codes with
  activity names and scope descriptions.
- Two new, independent `cost_codes` flags: `include_in_estimate`,
  `billable` — distinct from the pre-existing `fee_eligible`.
- Project financial setup fields the workbook requires: deposit %,
  estimate numbering, invoice prefix + draw counter, estimate terms text.
- Organization billing identity (payable-to name/address/phone/email).
- Client billing/contact information (project-scoped, no portal login
  required).
- A credit-applied tracking structure (append-only ledger).
- A vendor master table (org-scoped).

**Explicitly excluded, unchanged from the approved request:** estimates,
vendor quotes, change orders, QuickBooks import wiring, draws, invoices,
invoice lines. Nothing in this package reads or writes `budget_ledger`,
`expenses`, `committed_costs`, `forecast_entries`, or `fee_ledger`.

## Schema/migration changes

New migration: `schema/012_financial_master_data.sql` (+
`schema/012_financial_master_data_down.sql`). Full rationale is written
inline in the migration itself; summarized here:

| Table/change | Purpose |
|---|---|
| `divisions` | Per-project, mirrors `cost_codes`' own `unique(id, project_id)` composite-FK pattern (schema/001 precedent) |
| `cost_codes` +5 columns | `division_id`, `activity_name`, `scope_description`, `include_in_estimate`, `billable` |
| `vendors` | Org-scoped master data; no vendor-portal access policy (internal record-keeping, same posture as `committed_costs.vendor_name` today) |
| `project_financial_settings` | 1:1 with `projects`; deposit basis points, estimate/invoice numbering, draw counter, estimate terms text |
| `project_clients` | Project-scoped billing contacts, separate from `project_members`/`profiles` (no login required) |
| `credit_ledger` | Append-only (`reject_mutation()` trigger, same as `budget_ledger`/`fee_ledger`); staff-only visibility |
| `orgs` +7 columns, +1 policy | Billing identity fields; **first-ever UPDATE policy on `orgs`** (previously bootstrap-only) |
| `division_templates`, `cost_code_templates` | Global, read-only reference data — the digitized workbook itself |
| `apply_standard_cost_code_template(project_id)` | Staff-only RPC; copies the templates into a project's `divisions`/`cost_codes` once; rejects re-application |

## Why templates are a separate global table, not baked into the migration per-project

`divisions`/`cost_codes` are project-scoped and don't exist until a
project does. The templates give the 113-row dataset one canonical,
versioned home (`division_templates`/`cost_code_templates`, seeded once
by this migration) that `apply_standard_cost_code_template()` — the
"seed/import logic" the approved request asked for — copies from into
any real project. `scripts/db/seed.mjs` demonstrates the intended
end-to-end flow (reproduced directly rather than via the RPC — see
"Known limitations" below for why).

## RLS and audit posture

Every new table is RLS-enabled from creation, `to authenticated` only,
following the exact patterns already established in schema/001-011:

- `divisions`, `project_clients`: staff full access + client read
  (mirrors `cost_codes_staff_full`/`cost_codes_client_read`).
- `vendors`, `project_financial_settings`, `credit_ledger`: staff-only,
  no client policy (mirrors `committed_costs_staff_only`) — deliberately
  conservative where a field could carry internal commentary
  (`credit_ledger.note`) or where nothing downstream consumes the data
  client-side yet.
- `division_templates`, `cost_code_templates`: readable by any
  authenticated user (nothing sensitive), writable by neither — no
  insert/update/delete policy exists at all, and INSERT/UPDATE/DELETE
  are explicitly revoked from `authenticated`/`anon`.

Every mutable new table has a `log_audit()`-family trigger. One new
dedicated audit function was required: `log_audit_project_settings()`,
because `project_financial_settings` has no `id` column (its primary
key **is** `project_id`, one row per project) — `log_audit()` and
`log_audit_self_scoped()` both unconditionally reference `.id`, which
Postgres validates at first-execution time even for the untaken `CASE`
branch (the exact class of bug schema/006's own header comment
describes for `orgs`/`profiles` and `project_id`). Caught by actually
running the SQL test suite, not by review — see "How this was verified."

`audit_log_org_scoped_select` (schema/006) only covered `table_name IN
('orgs', 'profiles')`; a new additive policy,
`audit_log_vendors_staff_select`, extends the same pattern to `vendors`
so an org's own audit trail for vendor changes is actually queryable,
not just durably written.

## Unresolved decisions — flagged, not resolved

Per explicit instruction, these are preserved exactly as they appear in
the workbook. None of the six items below were changed by this package;
all are visible today by querying `cost_code_templates`/`cost_codes`
directly.

1. **`5011`, `5111`, `5170` carry an unexplained `***` marker** in their
   activity names (`Sheetrock - Sub ***`, `Ceramic Tile - Sub ***`,
   `Hardwoods - Sub ***`). No legend exists anywhere in the workbook.
   Reproduced verbatim, including the `***`, in `activity_name`.
2. **Inconsistent material/sub abbreviation style**: most codes use
   `- Mat`/`- Sub`; a cluster (`5030`/`5031`/`5035`/`5036`) uses
   `- M`/`- S`/`- Conc`/`- Sub` instead. Not normalized.
3. **Two "trim material" codes with unclear boundary**: `5049 Trim -
   Materials` and `5050 Trim -Int Doors - Mat`. Not merged or renamed.
4. **Possible scope overlap**: `6060 Fence` (Exterior Improvements &
   Closeout) vs. `7050 "Pool, pavers, Fence"` (Other Project Costs).
   Not reconciled.
5. **`7050` bundles three unrelated scope items** (`Pool, pavers,
   Fence`) into one code, unlike every other single-scope code. Not split.
6. **`7082`/`9999` combine `include_in_estimate = true` with `billable =
   false`** — a real, load-bearing combination (confirmed by this
   package's own test suite), not a data-entry error, but still worth a
   human confirming the business intent (client-facing estimate rollup
   includes a line the client is never actually billed for).

A decision on any of these belongs to whoever owns the cost-code list,
not to this package.

## Independent review

An independent review (fresh context, no prior involvement in writing
this package) checked RLS correctness/completeness, composite-FK
integrity, the `apply_standard_cost_code_template()` RPC's security
model, `credit_ledger`'s append-only enforcement, the 113-row seed
data's fidelity against a direct re-parse of the actual workbook file,
test-suite quality (no vacuous assertions; every new policy has
coverage), down-migration correctness, scope discipline, and the six
unresolved-decisions claim. **Verdict: ready to ship, no blocking
findings.** Two non-blocking Minor findings were fixed anyway before
sign-off:

1. `WORKBOOK-GAP-ANALYSIS.md` §1's per-division cost-code-count table
   had two swapped-looking numbers (Foundation listed as 15, Other
   Project Costs as 5) that didn't match the actual workbook (13 and 7
   respectively) — the total still happened to read 113, which is why
   it wasn't caught earlier. The migration's own seed data was always
   correct; only that one summary table in the gap-analysis doc was
   wrong. Fixed.
2. `vendors` and `project_financial_settings` DELETE was neither
   audited nor blocked, unlike every other mutable table in this
   schema (each is either delete-blocked or delete-audited). Fixed by
   adding a `vendors_no_delete` trigger (blanket reject, matching
   `committed_costs`/`forecast_entries`/`budget_suggestions`'s existing
   precedent — nothing references `vendors.id` yet, so there's no
   "unless unused" exception to make) and adding `delete` to both
   tables' audit triggers where blocking wasn't appropriate
   (`project_financial_settings.project_id` has `on delete cascade`
   from `projects`; a reject-delete trigger there would break that
   cascade the moment a project is ever deleted, so that table is
   delete-audited, not delete-blocked).

## Known limitations

- **`credit_ledger` has no reversal-magnitude enforcement trigger.**
  `budget_ledger`/`fee_ledger` (schema/001) both have
  `enforce_reversal_magnitude()`, which caps a reversal's magnitude
  against its original entry and rejects same-direction "reversals."
  `credit_ledger` deliberately does not reuse or duplicate that trigger
  yet — nothing reads from this ledger today (no invoice/draw logic
  exists), so the safety net has no consumer to protect. Add it when
  P6 (Billing: Draws) starts computing "credit applied" from this
  ledger for real.
- **`scripts/db/seed.mjs`'s cost-code-template application does not
  call `apply_standard_cost_code_template()`.** That RPC is `SECURITY
  INVOKER` and checks `is_org_staff(project_id)`, which requires a real
  `auth.uid()` — the seed script's service-role client has none, the
  same limitation the script already documents for
  `bootstrap_organization()`. The seed script instead reproduces the
  function's logic directly against `division_templates`/
  `cost_code_templates` via the service-role client. A real
  project-creation flow (future package), calling the RPC as an
  authenticated staff user, is unaffected.
- **`project_financial_settings` is a single mutable row per project,
  not an append-only ledger**, unlike `budget_ledger`/`fee_ledger`.
  Deliberate: nothing reads from it yet, so there is no already-issued
  estimate/invoice whose numbers a later edit here could silently move.
  When P4/P6 build estimates/invoices, **those tables must snapshot the
  values they used at creation time** — this settings table staying
  simple is not a substitute for that snapshot discipline.
- **Up→down→up reapply testing for migration 012 was run manually**
  (a throwaway PGlite script applying 001-012, then 012's down script,
  then 012 again — all three steps succeeded with zero errors) but is
  not wired into `scripts/db/run-sql-tests.mjs` as an automated CI
  check. This matches the current state of every other migration's down
  script in this repo (`001_core_financial_down.sql`'s own header
  documents the same "written, manually verifiable, not yet automated"
  status) — not a regression specific to this package.

## How this was verified

- `node scripts/db/run-sql-tests.mjs` — all 17 SQL files (migrations
  001-012 + all four test suites) applied/passed against a fresh
  PGlite (real Postgres-compiled-to-WASM) instance. This is genuine
  execution, not review: real RLS policies evaluated against real
  role-switched queries, real trigger/constraint enforcement, real
  `SECURITY DEFINER`/`SECURITY INVOKER` function calls.
- `tests/sql/package_p2_1_financial_master_data_tests.sql` (new, 9
  sections) proves, via actual queries rather than code review:
  template read-only access; `apply_standard_cost_code_template()`
  staff-only gating, successful application (7 divisions / 113 cost
  codes onto a project that already had one ad hoc cost code, for 114
  total), and rejection on re-application; `divisions`/`vendors`/
  `project_clients`/`project_financial_settings`/`credit_ledger` RLS in
  both directions (client read where intended, zero rows where not,
  cross-org isolation reusing the `org_b_admin` fixture from
  `package_p1_auth_tests.sql`); `credit_ledger`'s append-only
  enforcement (`UPDATE`/`DELETE` both rejected) and `entry_type`
  constraint; `project_financial_settings`'s deposit basis-points range
  constraint; the new `orgs` UPDATE policy in three directions (org
  admin succeeds, org staff is rejected, a different org's admin is
  rejected); and that `audit_log` actually captured the new tables'
  inserts (not just that the trigger exists).
- One real bug was caught by actually running this suite (not by
  review): the initial `project_financial_settings` audit trigger
  reused `log_audit()`, which fails at execution time because that
  table has no `id` column. Fixed by adding the dedicated
  `log_audit_project_settings()` function — see "RLS and audit posture"
  above.
- `npm run typecheck` / `npm run test` / `npm run build` — unaffected by
  this package (no TypeScript/application code touched; this is a
  schema-only package by design), re-run to confirm no regression.
- The workbook file itself (`docs/reference/Stone_Column_Cost_Plus_Blank_Template.xlsx`)
  is now tracked in git, per instruction.
