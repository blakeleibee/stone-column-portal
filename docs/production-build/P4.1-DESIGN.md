# P4.1 — Cost Code Breakdown (Child Budget Items) — Design Record

**Status:** Design only. Not yet implemented. Produced at the owner's
explicit request, pausing P5 after Task 6 (of 12) — Tasks 7–12 remain
un-started pending review of this document. Full requirement as given:
every project cost code must optionally support project-specific child
budget breakdown items underneath it (example given: `2031 Gravel` →
"Rough-construction gravel" / "Pre-slab gravel" / "Temporary erosion
gravel"), while the parent cost code remains the canonical,
QuickBooks-mapped entity.

## Recommendation, stated up front

**Yes — implement this as a focused, P2.1-shaped foundational package
(working name P4.1) before resuming P5 Task 7.** Reasoning:

1. **This is squarely P4's domain** (estimating/budgeting), not P5's.
   P2.1 is the exact precedent for inserting a foundational package
   between two others because the next package needs ground truth that
   doesn't exist yet — P2.1 was inserted before P4 itself for
   identical reasons ("P4 needs real cost-code granularity to build
   against... didn't exist yet," per `PRODUCTION-ROADMAP.md`).
2. **Zero already-shipped P5 TypeScript needs to change either way.**
   Research below confirms the two P5 RPCs this feature touches
   (`award_bid()`, `commit_material_order()`) have exactly one
   TypeScript caller each — `award_bid()`'s caller (Task 5,
   `bidService.ts`) needs no change at all, because its signature
   doesn't change. `commit_material_order()`'s signature *does*
   change (one new output column), but its only intended caller is
   Task 8's `procurementService.ts` — **which hasn't been written
   yet.** Doing this now means Task 8 is written once, against the
   final shape, instead of being written against the old shape and
   retrofitted days later.
3. **P5's remaining UI tasks (7, 9) directly benefit from having this
   in place first.** `/admin/commitments` (Task 7) and
   `/admin/procurement` (Task 9) are exactly the screens that would
   need to grow child-aware grouping/selectors — building them once,
   with children already real, avoids a second pass through both.
4. **The migration is small and genuinely additive** (nullable columns
   + one new table + two small RPC edits) — see "Existing-data
   compatibility" below. There is no scenario where doing this later
   is cheaper; every table it touches only grows more rows between now
   and later.

The rest of this document assumes that recommendation and designs
accordingly. If the owner instead wants P5 finished first, everything
below still applies unchanged as a later, standalone package — nothing
here is P5-Task-7-through-12-shaped, it's cost-code-shaped.

## The core architectural fact this design rests on

**`computeCategoryFinancials()` (`packages/01-financial-engine/src/budget.ts`)
already computes a parent cost code's rolled-up totals by filtering
every raw ledger/expense/committed-cost/forecast row down to
`e.costCodeId === costCode.id` — it has no idea a "child" concept
exists, and it doesn't need to.** This is the single fact that makes
the whole feature additive rather than a parallel model: a child is
just one more nullable column on rows that already belong to the
parent's `cost_code_id`. Add the column, and the parent's existing
rollup formula includes every child's rows automatically, with **zero
changes to that function** — "the parent displays rolled-up totals
across all children" is satisfied by the *absence* of a code change,
which is the strongest possible evidence this isn't a second financial
model living beside the first one.

## Scope

A new table, `cost_code_children`, project-scoped and FK'd to the
existing `(cost_code_id, project_id)` composite key exactly like every
other backbone table. A new nullable `cost_code_child_id` column,
composite-FK'd to `cost_code_children`, added to every table the owner
named: `budget_ledger`, `expenses`, `committed_costs`,
`forecast_entries`, `bid_packages`, `material_order_line_items`. Two
existing P5 RPCs (`award_bid()`, `commit_material_order()`) updated to
forward the new column. One existing P4 trigger
(`enforce_single_original_budget_entry`) updated to scope "one original
entry" per `(cost_code_id, cost_code_child_id)` pair, not per cost code
alone. A new pure rollup function in the financial engine. New UI: an
expand affordance on the Estimate table and the two read-only budget
tables (admin financials; client budget explicitly excluded, see
Decision 7).

## Decisions made in this design (flagged explicitly, per project convention)

1. **`cost_code_children` is a new table, not a self-referencing
   `parent_id` column on `cost_codes` itself.** A child is
   project-specific breakdown detail, never a QuickBooks-mapped,
   template-seeded, cross-project-comparable entity the way a real
   cost code is — conflating the two into one self-referencing table
   would let a child accidentally participate in cost-code-template
   seeding, QuickBooks item-override matching, or division rollups it
   has no business in. A separate table makes "children are not new
   global cost codes" true by construction, not by convention.

2. **Every existing financial/commitment table gets an *optional*,
   *nullable* `cost_code_child_id` column — never a required one, and
   never a second copy of `cost_code_id`.** This is what makes
   "existing transactions without a child remain valid" true with zero
   backfill: every row ever written before this migration already has
   `cost_code_child_id = null` implicitly, satisfying the "Unallocated"
   requirement without a single UPDATE statement. The composite FK on
   each new column is `(cost_code_child_id, cost_code_id, project_id)
   references cost_code_children(id, cost_code_id, project_id)` — the
   same shape `cost_codes` itself already uses for the parent-level FK,
   requiring `cost_code_children` to carry its own
   `unique (id, cost_code_id, project_id)`, mirroring
   `cost_codes`' own `unique (id, project_id)`. This is what stops a
   row from referencing a child that belongs to a *different* cost
   code than the row's own `cost_code_id` — a real data-integrity trap
   if left to application code alone, exactly the class of invariant
   this schema always pushes into the database itself.

3. **Delete-vs-archive is enforced by a trigger modeled directly on
   `cost_codes`' own `reject_cost_code_delete_if_used()`
   (schema/001) — not a new invention.** That function already
   implements exactly "delete allowed only if nothing references it
   yet; otherwise archive instead," checking existence across
   `budget_ledger`/`expenses`/`committed_costs`/`forecast_entries`.
   `cost_code_children` gets the identical pattern, checking the same
   four tables (plus `bid_packages`/`material_order_line_items`, which
   `cost_codes`' own guard predates and doesn't need to check, but a
   child does) for rows referencing `cost_code_child_id`.

4. **A child's `name` is unique per cost code only among *active*
   (non-archived) children — enforced via a partial unique index, not
   a plain table-wide unique constraint.** Plain uniqueness would
   permanently block reusing a name after archiving (e.g., archiving
   "Pre-slab gravel" for a scope-definition mistake, then wanting a
   fresh child with that same name later) — a partial index
   (`where not is_archived`) allows exactly that, while still
   preventing two simultaneously-active children under one code from
   sharing a name.

5. **`enforce_single_original_budget_entry` (P4, migration 013) must be
   widened from "one original entry per `cost_code_id`" to "one
   original entry per `(cost_code_id, cost_code_child_id)` pair,"
   using `is not distinct from` for the nullable column** — otherwise
   entering an original budget for the *parent* (unallocated,
   `cost_code_child_id is null`) would permanently block ever entering
   one for any *child* of the same code, or vice versa, since the
   current check only looks at `cost_code_id`. This is a required
   correction to existing P4 behavior, not a new invariant — the
   original intent ("one original entry, corrections after that") is
   preserved exactly, just now scoped to the right grain. Found during
   this design's own schema research, not something the owner asked
   for by name — flagged the same way every other self-identified gap
   in this project has been.

6. **QuickBooks import continues to resolve only to `cost_code_id` —
   it does not attempt to auto-resolve a child.** `parseQuickBooksCsv.ts`'s
   `resolveCostCodeId()` and `import_mapping_profiles`' matching
   strategies (`itemOverrides`/`exact`/`prefix`) stay completely
   untouched; `confirm_import_batch()`'s explicit 9-column INSERT list
   requires zero changes (a new nullable column not in that list just
   defaults to `null`, exactly like `corrects_expense_id` already
   does). A new, separate, small write function —
   `allocateExpenseToChild(supabase, expenseId, costCodeChildId | null)`
   — lets staff manually assign or reassign an already-imported
   expense's child *after* import, as a deliberate two-step workflow
   (import lands Unallocated under the correct parent; a human
   assigns finer detail afterward) rather than teaching the import
   pipeline a second matching dimension it wasn't asked to have.
   **Explicit owner decision, flagged for confirmation:**
   `cost_code_child_id` is deliberately **not** added to
   `enforce_expense_state_transition()`'s frozen-field list — a
   *posted* expense's child allocation may still be corrected after
   the fact, since reassigning which child an expense rolls up under
   changes categorization only, never the recognized dollar amount,
   parent cost code, vendor, or date the posting-freeze rule actually
   protects. If the owner wants child allocation frozen at posting
   too, this is a one-line addition to that trigger's existing
   field-comparison list.

7. **Client-facing budget screens (`ClientBudgetAndInvoicesScreen`)
   stay parent-level-only — child breakdown is not exposed to clients
   in this pass.** Nothing in the stated requirements asks for
   client-facing detail, and `CLAUDE.md`'s client-visibility rule
   (published status *and* an explicit visibility flag, never one
   alone) has no existing per-child visibility concept to hook into.
   Building one now would be scope the owner didn't ask for. Flagged
   as a deliberate, reversible exclusion — the schema doesn't prevent
   a later package from adding client visibility; it simply isn't
   built here.

8. **`material_orders.cost_code_id` (the order-level "convenience
   default," per P5 Decision 2) does *not* grow a matching
   `cost_code_child_id` convenience default.** Only
   `material_order_line_items` — the already-authoritative allocation
   grain — gets the new column, matching the owner's own phrasing
   ("material-order lines... optionally referencing a child," not
   "material orders"). Adding a second, order-level child default
   would be a UI nicety (pre-fill new lines' child selector) the owner
   didn't ask for and that adds a second "convenience, never
   authoritative" field to reason about for no stated benefit — can be
   added later as a pure UI enhancement with zero schema change if
   wanted.

9. **The financial engine gets a new function, `computeChildBreakdown()`,
   built by extracting a shared internal summation helper out of
   `computeCategoryFinancials()` rather than hand-duplicating its
   formula.** Two independent implementations of the same sum-by-status
   logic is exactly the failure class `CLAUDE.md`'s "no screen computes
   its own financial numbers" rule exists to prevent, extended here to
   "no two engine functions compute the same formula independently."
   The refactor changes `computeCategoryFinancials()`'s internals only
   — its external signature, inputs, and outputs are byte-identical to
   today, proven by re-running its own existing test suite completely
   unmodified as part of this package's own test gate (Task 1 below).

10. **A bid package supports at most one child target, matching P5
    Decision 1's "single-cost-code" bid-package shape exactly one
    level deeper** — `bid_packages.cost_code_child_id` is a single
    nullable column, not a line-item table. A bid whose real scope
    spans two children (like two cost codes) is split into two bid
    packages, the same trade-off P5 Decision 1 already accepted and
    documented for cost codes themselves.

## Schema/migration changes

One new migration, `schema/016_cost_code_children.sql` (+ down),

**`cost_code_children`:**
```sql
create table cost_code_children (
  id                uuid primary key default uuid_generate_v4(),
  project_id        uuid not null references projects(id) on delete cascade,
  cost_code_id      uuid not null,
  name              text not null,
  scope_description text,
  sort_order        integer not null default 0,
  is_archived       boolean not null default false,
  created_by        uuid references profiles(id),
  created_at        timestamptz not null default now(),

  constraint cost_code_children_cost_code_project_fk
    foreign key (cost_code_id, project_id) references cost_codes(id, project_id),
  -- Enables composite FKs from every child-aware table below, mirroring
  -- cost_codes' own unique(id, project_id) (Decision 2).
  unique (id, cost_code_id, project_id)
);

-- Active-only uniqueness (Decision 4) — a plain table-wide unique
-- constraint would permanently block reusing a name after archiving.
create unique index cost_code_children_name_unique_active
  on cost_code_children (cost_code_id, name) where not is_archived;

alter table cost_code_children enable row level security;

create policy cost_code_children_staff_full_access on cost_code_children
  for all to authenticated
  using (is_org_staff(project_id)) with check (is_org_staff(project_id));

create trigger audit_cost_code_children after insert or update or delete on cost_code_children
  for each row execute function public.log_audit();

-- Delete-vs-archive guard (Decision 3), modeled directly on
-- reject_cost_code_delete_if_used() (schema/001:596-613).
create or replace function public.reject_cost_code_child_delete_if_used() returns trigger
language plpgsql
set search_path = public, pg_temp
as $$
begin
  if exists (select 1 from public.budget_ledger where cost_code_child_id = OLD.id)
     or exists (select 1 from public.expenses where cost_code_child_id = OLD.id)
     or exists (select 1 from public.committed_costs where cost_code_child_id = OLD.id)
     or exists (select 1 from public.forecast_entries where cost_code_child_id = OLD.id)
     or exists (select 1 from public.bid_packages where cost_code_child_id = OLD.id)
     or exists (select 1 from public.material_order_line_items where cost_code_child_id = OLD.id)
  then
    raise exception 'Cost code child % is in use and cannot be deleted. Archive it instead (is_archived = true).', OLD.id;
  end if;
  return OLD;
end;
$$;

create trigger cost_code_children_no_delete_if_used before delete on cost_code_children
  for each row execute function public.reject_cost_code_child_delete_if_used();
```

**`enforce_single_original_budget_entry` (Decision 5) — widened, not

```sql
create or replace function public.enforce_single_original_budget_entry() returns trigger
language plpgsql
as $$
begin
  if new.entry_type = 'original' and exists (
    select 1 from public.budget_ledger
    where cost_code_id = new.cost_code_id
      and cost_code_child_id is not distinct from new.cost_code_child_id
      and entry_type = 'original'
  ) then
    raise exception 'Cost code % (child %) already has an original budget entry — use an adjustment (correction) instead.',
      new.cost_code_id, coalesce(new.cost_code_child_id::text, '<unallocated>');
  end if;
  return new;
end;
$$;
```
(Trigger itself, `enforce_single_original_budget_entry before insert on
budget_ledger`, is unchanged — only the function body above changes.)

**`award_bid()` (P5, schema/015) — forwards the package's child, no
signature change:**
```sql
create or replace function public.award_bid(p_bid_submission_id uuid)
returns uuid
language plpgsql security invoker set search_path = public, pg_temp
as $$
declare
  v_submission bid_submissions%rowtype;
  v_package bid_packages%rowtype;
  v_committed_cost_id uuid;
begin
  select * into v_submission from bid_submissions where id = p_bid_submission_id for update;
  if not found then
    raise exception 'Bid submission % not found', p_bid_submission_id;
  end if;
  if v_submission.status <> 'submitted' then
    raise exception 'Bid submission % must be in status ''submitted'' to award (currently %)',
      p_bid_submission_id, v_submission.status;
  end if;

  select * into v_package from bid_packages where id = v_submission.bid_package_id for update;

  insert into committed_costs (project_id, cost_code_id, cost_code_child_id, vendor_name, amount_cents, source_type, source_id)
  select bp.project_id, bp.cost_code_id, bp.cost_code_child_id, v.name, v_submission.amount_cents, 'bid_award', v_submission.id
  from bid_packages bp join vendors v on v.id = v_submission.vendor_id
  where bp.id = v_package.id
  returning id into v_committed_cost_id;

  update bid_submissions set status = 'awarded' where id = v_submission.id;
  update bid_submissions set status = 'declined'
    where bid_package_id = v_package.id and id <> v_submission.id and status = 'submitted';
  update bid_packages set status = 'awarded' where id = v_package.id;

  return v_committed_cost_id;
end;
$$;
```
**Zero change needed to Task 5's already-shipped `awardBid()` TypeScript
wrapper** — same input, same return type, same RPC name.

**`commit_material_order()` (P5, schema/015) — return shape changes,
grouping deepens by one column:**
```sql
create or replace function public.commit_material_order(p_material_order_id uuid)
returns table(cost_code_id uuid, cost_code_child_id uuid, committed_cost_id uuid)
language plpgsql security invoker set search_path = public, pg_temp
as $$
declare
  v_order material_orders%rowtype;
  v_vendor_name text;
  v_line record;
  v_new_committed_cost_id uuid;
  v_line_item_count integer;
begin
  select * into v_order from material_orders where id = p_material_order_id for update;
  if not found then
    raise exception 'Material order % not found', p_material_order_id;
  end if;
  if v_order.status <> 'draft' then
    raise exception 'Material order % must be in status ''draft'' to commit (currently %)',
      p_material_order_id, v_order.status;
  end if;

  select count(*) into v_line_item_count from material_order_line_items where material_order_id = v_order.id;
  if v_line_item_count = 0 then
    raise exception 'Material order % has no line items to commit', p_material_order_id;
  end if;

  select name into v_vendor_name from vendors where id = v_order.vendor_id;

  for v_line in
    select mo_li.cost_code_id as cc, mo_li.cost_code_child_id as ccc,
           sum(mo_li.quantity * mo_li.unit_price_cents)::bigint as total_cents
    from material_order_line_items mo_li
    where mo_li.material_order_id = v_order.id
    group by mo_li.cost_code_id, mo_li.cost_code_child_id
  loop
    insert into committed_costs (project_id, cost_code_id, cost_code_child_id, vendor_name, amount_cents, source_type, source_id)
    values (v_order.project_id, v_line.cc, v_line.ccc, v_vendor_name, v_line.total_cents, 'material_order', v_order.id)
    returning id into v_new_committed_cost_id;

    cost_code_id := v_line.cc;
    cost_code_child_id := v_line.ccc;
    committed_cost_id := v_new_committed_cost_id;
    return next;
  end loop;

  update material_orders set status = 'ordered', ordered_at = now() where id = v_order.id;

  return;
end;
$$;
```
`group by mo_li.cost_code_id, mo_li.cost_code_child_id` correctly
buckets every line with `cost_code_child_id is null` together as one
"Unallocated" group per cost code, per standard SQL `GROUP BY` NULL
handling — no special-casing needed. **This is the one real signature
change in this whole package** (`returns table(cost_code_id,
committed_cost_id)` → `returns table(cost_code_id, cost_code_child_id,
committed_cost_id)`), and it has zero existing caller to break — P5
Task 8, the only intended caller, has not been written yet.

## Financial engine changes

`packages/01-financial-engine/src/budget.ts`:
- Extract a private helper (name TBD at implementation time, e.g.
  `sumBucketFinancials`) containing `computeCategoryFinancials()`'s
  existing per-status summation logic, parameterized by a row-filter
  predicate instead of a hardcoded `costCode.id` comparison.
  `computeCategoryFinancials()` becomes a thin wrapper calling it with
  `(row) => row.costCodeId === costCode.id` — same public signature,
  same return shape, proven byte-identical via its own existing test
  suite re-run unmodified (Decision 9).
- New `computeChildBreakdown(costCode, children, ledgerEntries,
  expenses, committedCosts, forecastEntries): ChildBreakdownRow[]` —
  calls the same shared helper once per child (filter predicate adds
  `&& row.costCodeChildId === child.id`) plus once more for the
  synthetic `{ id: null, name: "Unallocated" }` bucket (filter:
  `row.costCodeChildId == null`). Returned array always includes the
  Unallocated row, even when its total is zero, so the UI never has to
  special-case "no unallocated activity" as "no row."

2. Active-only unique-name index: two active children with the same

3. Delete-vs-archive guard: an unused child deletes cleanly; a child
   referenced by a `budget_ledger`/`expenses`/`committed_costs`

## Acceptance criteria

1. `2031 Gravel` (or any real cost code) can have three children
   created, renamed, and reordered through the Estimate UI, each
   accepting its own original budget entry independently of the
   parent and of each other.
2. An expense imported via QuickBooks lands Unallocated under its
   parent cost code exactly as before this package existed, with zero
   behavior change to the import wizard; staff can then reassign it to
   a specific child afterward, including after it's `posted`.
3. A material order with line items split across two children of one
   cost code, once committed, produces one `committed_costs` row per
   child (plus one for any unallocated line), each correctly summed,
   discoverable via the RPC's own returned mapping — not merely "the
   right number of rows exist."
4. Attempting to delete a child with any financial history is
   rejected with a clear message directing the user to archive
   instead; an unused child deletes cleanly.
5. The parent cost code's rolled-up total, before and after this
   migration, is provably identical for any existing project's data —
   proven by re-running `computeCategoryFinancials()`'s own existing
   test suite unmodified and confirming identical output.
6. `npm ci`/`typecheck`/`test`/`build` all pass from a clean install;
   migration 016 applies cleanly to the real hosted dev project
   alongside 001–015.

## Dependencies

P4 (cost codes, budget ledger, QuickBooks import — the domain this

## Explicit exclusions

No client-facing child visibility (Decision 7). No QuickBooks
auto-resolution of children (Decision 6) — import stays parent-level,
manual reassignment only. No order-level convenience-default child on
`material_orders` (Decision 8). No change to `budget_suggestions` —
the system-suggestion engine stays cost-code-level only; nothing in
the stated requirements calls for suggestion-level child awareness,
and it's the one backbone table with no owner-named requirement to
extend, so it's left alone rather than extended speculatively. No
change to `fee_ledger` or fee computation — fees are already computed
at the cost-code level from `computeCategoryFinancials()`'s output,
which is unaffected by this package (Decision 9's core guarantee), so
nothing about fee accrual changes even implicitly.
