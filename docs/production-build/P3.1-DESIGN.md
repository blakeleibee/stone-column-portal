# P3.1 — Project Intake & Employee Handoff (Design)

**Status:** Draft — awaiting owner approval. Do not implement, merge, tag, or
resume P5 until this design and its companion plan
(`docs/superpowers/plans/2026-08-26-p3.1-project-intake-and-handoff.md`) are
approved.

**Relationship to P3:** P3.1 is an amendment to the already-implemented,
owner-preview-stage P3 ("Project & Staff Access Foundation"), not a
standalone future package — it revises P3's own project-creation screen
before `p3-complete` is tagged. Named `P3.1` to match the existing
sub-package convention (`P2.1`), not `P16` or similar. **Consequential
decision 1** (see §9) asks the owner to confirm this placement.

**Trigger:** Owner review of the P3 create-project form found it structured
around premature contract pricing (fixed fee, fee percentage, a manually
typed/"suggested" project number) rather than around what a project actually
needs at the moment a lead becomes a real opportunity: identification,
assignment, and a place to accumulate what's known so staff can be handed
the project responsibly. This document redesigns that moment.

## 0. What already exists (research summary — see full agent reports for file:line detail)

- `projects.project_number` is a bare `text`, required, `unique(org_id,
  project_number)` — no format, no generator. Caller-supplied via the
  `create_project_with_defaults()` RPC's `p_project_number` parameter today.
  No sequence/counter of any kind exists anywhere in the schema for it. The
  closest precedent is `project_financial_settings.next_estimate_number` — a
  plain mutable-integer counter, per-project (not per-org-per-year), and
  currently unread by any live code.
- `create_project_with_defaults()` (`schema/016:620-687`) is a single
  `SECURITY INVOKER`, admin-only, atomic RPC. It inserts `projects`,
  `project_fee_rules` (required today — percentage XOR fixed, both fields
  currently non-optional), seeds the standard cost-code template, and
  optionally inserts initial staff/client assignments.
- `projects.pricing_model` is `not null` with no "undetermined" value.
  `pricing_model_label` is a free-text column that **is** actively used —
  a real create-form field, rendered in the project list, and rendered on
  both `AdminOverviewScreen.tsx`/`AdminFinancialsScreen.tsx` via
  `supabaseFinancialRepository.getProjectMeta()`'s `pricingLabel`. (An
  earlier draft of this document claimed it was unused and cited a
  Completeness Matrix note that does not actually exist — corrected here;
  see §2.)
- `project_clients` (`schema/012:225-258`) already exists — one row per
  contact, portal-login-free, explicitly designed for billing/decision
  contacts distinct from `profiles`/`project_members`. It is **schema-only
  today**: no service function or UI reads or writes it. Columns: `id,
  project_id, full_name, email, phone, address, city, state, zip,
  is_primary, created_by, created_at`.
- `project_decision_makers` does **not exist**. `CLIENT-APPROVAL-MODEL.md`
  deliberately reserves that table's design for P7 — it defines *what* the
  eventual approval-authority model must support, not a schema.
- `documents` (`schema/010`) is a real, RLS-backed, audited **metadata**
  table (`storage_key` text pointer) — but no Supabase Storage bucket, no
  upload endpoint, and no UI anywhere reads or writes it. Per
  `TARGET-ARCHITECTURE.md` §8, the eventual durable store is
  OneDrive/SharePoint via Microsoft Graph (P9), not Supabase Storage.
  Functionally absent for this package's purposes.
- `projects.phase`, `projects.start_date`, `projects.target_completion_date`
  already exist as plain columns never *set* by the current create form
  (still true), but `phase` **is** already read and rendered today —
  `supabaseFinancialRepository.ts` selects it and `AdminFinancialsScreen.tsx`
  renders it raw (`{projectMeta.phase} phase`). Currently always empty in
  practice since nothing writes it. No new columns needed for phase/timing
  — see §5, which also notes the one display update this implies.
- `project_staff_assignments` (`schema/016:116-127`) columns: `id,
  project_id, profile_id, assigned_at, assigned_by, revoked_at, revoked_by,
  created_at`. Writes are gated by `project_staff_assignments_admin_manage`
  — **admin-only**, deliberately not `is_org_staff_for_org()` (closes the
  self-escalation bug found in P3's own independent review). Any new
  columns on this table inherit the same admin-only write policy for free.
- Audit convention: `log_audit()` trigger (`schema/001:772`), attached as
  `after insert or update [or delete] ... for each row execute function
  public.log_audit()` to any table with a `project_id` column. New tables
  below follow this exactly.
- `FINANCIAL-ARCHITECTURE.md`'s ledger backbone (`budget_ledger`,
  `fee_ledger`, `committed_costs`, `forecast_entries`, `cost_codes`, via the
  `(cost_code_id, project_id)` composite FK) is the one thing no package may
  duplicate. Nothing in this design touches or parallels it — see §5's
  "preliminary budget range" reasoning.

## 1. Automatic project numbering

**Format:** `SC-YYYY-###` (e.g. `SC-2026-001`), zero-padded to 3 digits
minimum, growing naturally past 999 (`SC-2026-1000`) rather than truncating
— gaps are acceptable, silent truncation is not.

**QuickBooks compatibility check:** No existing or planned QuickBooks
integration point (`P4`'s import wizard, `P4.4`'s still-undesigned export)
imposes a format requirement on `project_number` — it's read as plain text
wherever it's used, and `P4.4`'s eventual customer:job mapping is a
separate, explicit mapping table, not a parsed/derived field. No reason to
deviate from `SC-YYYY-###`.

**Mechanism** — new table, atomic upsert, no browser involvement:

```sql
create table project_number_counters (
  org_id      uuid not null references orgs(id),
  year        integer not null,
  next_number integer not null default 1,
  primary key (org_id, year)
);

alter table project_number_counters enable row level security;
-- No policies at all, matching audit_financial_tables' existing precedent
-- (schema/016) for a table meant to be reachable only through a
-- SECURITY DEFINER function, never directly by an authenticated caller.
revoke all on project_number_counters from authenticated, anon;
```

Numbering happens inside a new `SECURITY DEFINER` helper,
`generate_project_number(p_org_id uuid) returns text`, called by
`create_project_with_defaults()` itself (never exposed as a standalone
caller-invokable RPC — it has no authorization check of its own because it's
only ever called from within an already-admin-gated function):

```sql
insert into project_number_counters (org_id, year, next_number)
values (p_org_id, v_year, 2)
on conflict (org_id, year)
  do update set next_number = project_number_counters.next_number + 1
returning next_number - 1 into v_sequence;
```

`v_year := extract(year from now())::int` — computed server-side at
generation time. The single-statement `INSERT ... ON CONFLICT DO UPDATE
... RETURNING` is Postgres's standard atomic-increment idiom: it takes a
row-level lock as part of the same statement, so two concurrent
`create_project_with_defaults()` calls for the same org in the same year
serialize on that row and always receive distinct, sequential values — no
explicit `SELECT ... FOR UPDATE`, no advisory lock, no application-level
retry loop needed.

- **Uniqueness:** guaranteed within the counter's own sequence. Collision
  against a pre-existing, manually-typed legacy number that happens to
  match the generated string exactly (e.g., someone once typed literally
  `SC-2026-004`) is astronomically unlikely and, if it ever happened, fails
  loudly via the existing `projects_number_unique_per_org` constraint rather
  than silently duplicating — correct fail-closed behavior, not a gap.
- **Never reused after archival:** the counter is monotonic and never
  decremented on archive, status change, or (there is no delete path)
  deletion — automatically satisfied, no extra logic needed.
- **Existing project numbers remain unchanged:** this migration touches no
  existing `projects` rows. `project_number_counters` starts empty; it is
  never backfilled from existing data, so old free-text numbers (however
  they were entered) are left exactly as they are.
- **Safe under simultaneous creation:** see the atomic-upsert mechanism
  above.
- **Read-only/immutable after assignment:** no UPDATE path is ever added for
  `projects.project_number` — same as today (nothing currently updates it).
- **Display:** unchanged rendering — project list, header switcher, brief,
  and (later) QuickBooks mapping all already display `projects.project_number`
  verbatim as plain text; no downstream change needed.

`create_project_with_defaults()`'s `p_project_number` parameter is removed
entirely (not deprecated-but-accepted) — the RPC generates it internally.
`ProjectListWorkspace.tsx`'s `suggestNextProjectNumber()` client-side
heuristic and its "Suggest next number" button are deleted, not hidden —
there is nothing left for the browser to suggest.

## 2. Intake instead of premature pricing

**Schema changes:**

- `projects.pricing_model` becomes **nullable** (`NULL` = "to be
  determined"). No new enum value — `NULL` is the standard SQL idiom for
  "unset," and avoids every future consumer needing to special-case a magic
  string alongside real values. See consequential decision 4.
- `projects.pricing_model_label` is **kept, not dropped** — corrected from
  an earlier draft of this document that wrongly claimed it was unused. It
  genuinely is read: `ProjectListWorkspace.tsx` renders it per row,
  `supabaseFinancialRepository.getProjectMeta()` selects it, and both
  `AdminOverviewScreen.tsx`/`AdminFinancialsScreen.tsx` render it as
  `pricingLabel` — a real, clearly-useful business purpose (a
  human-readable pricing summary, e.g. "Cost-plus 15%") that satisfies the
  owner's own keep-it condition. What changes is *when* it's set: it moves
  out of the create panel (§3 drops it along with every other pricing
  field) and becomes settable together with `pricing_model` and the fee
  terms via the new `set_project_fee_terms()` RPC (below) — one surface
  for every pricing-related field, filled in whenever pricing is actually
  decided rather than guessed at creation. Every existing display consumer
  keeps working unchanged, simply showing nothing until it's set — the
  same graceful-empty pattern those consumers already use.
- `create_project_with_defaults()`'s fee parameters
  (`p_pricing_model`, `p_fee_basis`, `p_fee_basis_points`,
  `p_fee_fixed_amount_cents`) all become optional (default `NULL`). The
  function only inserts a `project_fee_rules` row when a supported pricing
  model (`cost_plus_percentage` or `cost_plus_fixed_fee` — unchanged from
  today's `FEE_SUPPORTED_PRICING_MODELS` restriction) **and** matching fee
  data are both provided; otherwise it skips that insert entirely, leaving
  the project with no fee rule yet. This is not a new financial model — it
  is the same `project_fee_rules` table, now optionally populated later
  instead of mandatorily populated at creation.
- **New capability, not previously possible at all:** `project_fee_rules`
  and `projects.pricing_model` currently have no update path outside of
  creation. Since deferring pricing at creation is meaningless unless
  someone can come back and set it, this package adds a `set_project_fee_terms()`
  RPC (admin-only, same authorization as creation — see consequential
  decision 5) that inserts-or-supersedes `project_fee_rules` and updates
  `projects.pricing_model` together, atomically. This becomes the new
  "Contract & Pricing Terms" setup-checklist step (§9). `set_project_fee_terms()`
  optionally accepts a `p_pricing_model_label` argument alongside the
  structured fee data, so the label and the terms it describes are always
  set together, never drifting apart.

**UI changes:** the create-project panel drops every pricing field
(pricing model select, pricing-model-label input, fee-percent/fee-fixed
inputs) entirely. Pricing/contract terms — including the label — move to
the post-creation Setup screen, filled in whenever the business decision is
actually made — never fabricated or defaulted to make the form "complete."

## 3. Progressive creation workflow

**Minimum fields to create a project** (all that's required to identify and
assign the opportunity):

- Working project name (required)
- Project number — not a field; auto-assigned, shown as read-only after
  creation
- Project type (required — existing `PROJECT_TYPE_OPTIONS` select +
  "Other" free text, unchanged from current P3 implementation)
- Primary homeowner/contact — inline create-or-select (see §4). Recommended
  **optional** at this exact step (a lead can exist before a homeowner
  identity is fully confirmed), but this is a real judgment call the owner
  didn't explicitly settle — see consequential decision 9.
- Project location, or an explicit "Address not established" toggle (a
  project can exist before a site is confirmed — e.g. a lead still shopping
  lots)
- Short project concept (one to two sentences, required — this is the
  single free-text field a PM needs to make sense of "what is this," stored
  as `project_briefs.summary`)
- Assigned staff (existing picker, optional — unchanged from current P3
  decision that initial assignment is optional)

Everything else in §§4–8 lives on the post-creation Setup/Brief screen,
reachable immediately after "Save as Draft" (which is what creation already
does — every new project starts at `status='draft'`) and revisitable at any
time. No new "draft the draft" state is needed: `status='draft'` already
means exactly "created, not yet started," and the existing reversible
lifecycle (schema/017) is untouched.

## 4. Homeowner and decision-maker information

**Extends `project_clients` in place — does not duplicate it or touch
`project_decision_makers`/`CLIENT-APPROVAL-MODEL.md` (that remains P7's
scope exactly as already decided).** New nullable columns, all additive:

```sql
create type contact_role as enum (
  'primary_homeowner', 'secondary_homeowner', 'other_household', 'professional_contact'
);
create type contact_method as enum ('email', 'phone', 'text');
create type contact_info_status as enum ('not_started', 'requested', 'partial', 'complete');

alter table project_clients
  add column preferred_name          text,
  add column role                    contact_role,
  add column preferred_contact_method contact_method,
  add column is_decision_maker       boolean not null default false,
  add column is_billing_contact      boolean not null default false,
  add column info_status             contact_info_status not null default 'not_started';
```

- `is_decision_maker` is **informational only** — it tells staff "ask this
  person," nothing more. It confers no approval authority, has no
  effective-date history, and does not participate in any approval-response
  workflow. This is explicitly *not* an early implementation of
  `project_decision_makers`; when P7 builds the real model,
  `is_decision_maker=true` rows are the natural migration seed, but nothing
  here should be read as pre-empting that design. Flagged as consequential
  decision 6 because it sits directly adjacent to a standing architectural
  boundary.
- `is_billing_contact` is separate from `is_primary` (already exists) —
  the primary contact and the billing contact are frequently, but not
  always, the same person.
- Existing `address`/`city`/`state`/`zip` columns are reused as-is for
  "mailing address if different" (matches the table's original design
  comment).
- "How the lead/project originated" is **not** a per-contact field — it
  describes the project, not the person — so it lives on `project_briefs`
  (§5) as `lead_source`, not here.
- Multiple contacts per project already works today (no row-count
  constraint on `project_clients`) — "secondary homeowner/spouse" is simply
  a second row with `role='secondary_homeowner'`.
- No new RLS policy needed: `project_clients_staff_full`/`_client_read`
  already exist and govern every column on the table, including the new
  ones.
- No new audit trigger needed if one already covers `project_clients`;
  otherwise this package adds the standard `log_audit()` trigger alongside
  the column migration (confirm at implementation time — the two research
  passes didn't confirm whether one already exists on this specific table).

**UI:** an inline "add/edit contact" form reachable both from the create
panel (quick-add for the primary homeowner) and from the Setup screen's
"Homeowners & Decision-Makers" section (full list, add/edit/any number of
rows). No duplicate contact-entry surface is created — one form, two entry
points.

**Deliberately not built now:** any homeowner-facing intake-request flow
(a link a homeowner could fill in themselves), email delivery, or
questionnaire logic. `info_status` is set by *staff*, manually, reflecting
what staff currently knows — it is a status field, not a trigger for any
automated outreach. A future self-service intake package can read/write the
same columns without a redesign.

## 5. Project concept and scope

**New table, 1:1 with `projects`** (same pattern as `project_financial_settings`):

```sql
create table project_briefs (
  project_id                    uuid primary key references projects(id) on delete cascade,
  summary                       text,             -- required at creation (§3); editable after
  known_scope                   text,
  client_goals                  text,
  must_haves                    text,
  wishlist_items                text,
  known_exclusions              text,
  quality_expectations          text,
  approx_square_footage         integer,
  stories                       numeric,
  bedrooms                      integer,
  bathrooms                     numeric,          -- numeric, not integer: half-baths (2.5)
  target_budget_low_cents       bigint,
  target_budget_high_cents      bigint,
  confidence_note                text,             -- free text this pass — see decision 8
  lead_source                   text,
  internal_notes                text,             -- staff-only, never client-visible
  client_facing_notes           text,
  client_facing_notes_published boolean not null default false,
  updated_by                    uuid references profiles(id),
  updated_at                    timestamptz not null default now(),
  created_at                    timestamptz not null default now(),
  constraint target_budget_range_consistent check (
    target_budget_low_cents is null or target_budget_high_cents is null
    or target_budget_low_cents <= target_budget_high_cents
  )
);
```

- **Phase** and **desired timing** are *not* new columns — `projects.phase`
  (currently `text`, unused) is converted to a proper
  `project_phase` enum (`'lead', 'feasibility', 'preconstruction',
  'pricing', 'contract_pending', 'ready_to_start'`) since it's genuinely
  unused today (safe type change, confirmed by research: the current create
  form never sets it). `projects.start_date`/`target_completion_date`
  (also currently unused) are reused directly for "desired start/completion
  timing" rather than adding parallel `desired_*` columns.
- **Target budget range is deliberately outside the ledger backbone.** It
  is two plain `bigint` cents columns on an intake table, never written to
  `budget_ledger`/`fee_ledger`, never joined to `cost_codes`, and never
  read by any financial-engine calculation. This is categorically different
  from the "fixed-price contract amount" gap the Completeness Matrix already
  flagged as "exactly the parallel financial model `FINANCIAL-ARCHITECTURE.md`
  forbids" — that gap was about a *binding* dollar figure masquerading as
  ledger data; this is an explicitly non-binding, staff-entered signal shown
  with a permanent "Preliminary — not a budget or contract" label everywhere
  it's rendered, same spirit as the existing "suggested numbers are never
  official until accepted" non-negotiable. Flagged as consequential decision
  7 given the proximity to a standing architectural rule — worth an explicit
  owner sign-off rather than a silent assumption.
- **`internal_notes` vs. `client_facing_notes`** follow the existing
  client-visibility non-negotiable exactly: `client_facing_notes` is only
  ever exposed to a client-role session when `client_facing_notes_published
  = true` — the same "status AND explicit visibility flag" pattern already
  used elsewhere (`documents.is_published_to_client`), not a new pattern.
  `internal_notes` has no client-read RLS policy at all, ever.
- **Confidence/readiness (`confidence_note`):** owner gave an explicit
  6-value list for `phase` but no explicit taxonomy for confidence — kept
  as free short text for this pass rather than guessing a controlled list;
  can become an enum once real usage shows the right values (decision 8).
- RLS: new `project_briefs_staff_full` (`using/with check (is_org_staff(project_id))`,
  matching `project_clients`'s pattern — not financial, so not
  `is_financial_staff`), plus a client-read policy scoped to
  `client_facing_notes`-bearing columns only being meaningfully exposed
  when published (enforced by the UI/service layer reading the flag, since
  Postgres RLS is row-level not column-level — the repository read for
  client sessions simply omits `internal_notes` from the selected columns
  entirely, never relying on RLS alone to hide it). Audit trigger: **not**
  `log_audit()` — that function indexes `record_id` off `NEW.id`/`OLD.id`,
  and `project_briefs` has no `id` column (its primary key is
  `project_id`, same shape as `project_financial_settings`). This exact
  case is already solved in this schema — `schema/012` wrote
  `log_audit_project_settings()` specifically for `project_id`-keyed 1:1
  tables, and its body is already generic (keys off `tg_table_name`, not a
  hardcoded table name). Reuse that existing function; do not write a new
  one.
- **Structured vs. narrative:** per the owner's own instruction, only
  fields useful for searching/filtering are structured (square footage,
  bed/bath counts, phase, budget range); goals/must-haves/wishlist/
  exclusions/quality stay as flexible narrative text for this pass, not
  arrays — matches "preserve a flexible narrative area for unusual
  projects" and avoids overbuilding a taxonomy nobody's validated yet.

## 6. Property, design and permitting information

**Second new table, 1:1 with `projects`** — kept separate from
`project_briefs` because it has a different natural future owner (P13
Permits & Inspections will extend this table directly; P4.1/P4.3
estimating will extend `project_briefs`), matching the existing pattern of
keeping distinct future-package concerns in distinct tables rather than one
growing mega-table:

```sql
create type intake_item_status as enum (
  'unknown', 'requested', 'received', 'not_applicable', 'complete'
);

create table project_site_info (
  project_id                    uuid primary key references projects(id) on delete cascade,
  full_address                  text,             -- structured beyond projects.address if needed
  parcel_id                     text,
  ownership_status               text,             -- e.g. "owned", "under contract", "shopping lots"
  occupied_during_work           boolean,
  permitting_jurisdiction        text,
  hoa_review_required            boolean,
  hoa_status                     intake_item_status not null default 'unknown',
  zoning_notes                   text,
  survey_status                  intake_item_status not null default 'unknown',
  architectural_plans_status     intake_item_status not null default 'unknown',
  septic_or_sewer                text,             -- e.g. "septic", "public sewer", "unknown"
  water_source                   text,             -- e.g. "well", "public water", "unknown"
  utilities_available            text,
  soil_environmental_status      intake_item_status not null default 'unknown',
  soil_environmental_notes       text,             -- e.g. "flood zone AE", paired note like every other status field
  site_access_notes              text,
  financing_status               intake_item_status not null default 'unknown',
  permit_status                  intake_item_status not null default 'unknown',
  required_approvals_notes       text,
  updated_by                     uuid references profiles(id),
  updated_at                     timestamptz not null default now(),
  created_at                     timestamptz not null default now()
);
```

- Fields that are simple facts (parcel ID, zoning notes, utilities,
  occupied-during-work) are plain nullable columns — their presence or
  absence *is* the missing-information signal, no separate status column
  needed.
- Fields that describe a genuine in-progress *process* (survey,
  architectural plans, HOA review, soil/environmental report, financing,
  permits) get the shared `intake_item_status` enum
  (`unknown/requested/received/not_applicable/complete`) — this is the
  concrete implementation of "the screen should show Unknown, Requested,
  Received, Not Applicable or Complete where appropriate," applied only
  where it's genuinely meaningful rather than bolted onto every field.
- **Financing/lender status deliberately captures only a status enum and a
  free-text note** — never an account number, loan amount, or other
  sensitive financial detail, matching the owner's explicit "without
  collecting unnecessary sensitive financial data."
- **Engineer/designer/architect contacts are deliberately not columns on
  this table.** An earlier draft included `designer_contact_name`/
  `designer_contact_info` here, which would have created exactly the
  duplicate contact-entry surface the owner explicitly ruled out in §4 —
  `project_clients` already gained a `role` value
  (`'professional_contact'`, §4) for precisely this case. One surface: a
  designer/architect/engineer is a `project_clients` row like any other
  contact; `project_site_info` only tracks the *status* of plans/survey
  work, not who to call about it.
- RLS: `project_site_info_staff_full` (`is_org_staff(project_id)`, same
  shape as `project_clients`/`project_briefs`), no client-read policy (this
  is internal working information; add one later only if a real reason
  emerges — none was requested). Audit trigger: `log_audit_project_settings()`
  (reused, same reasoning as §5 — this table is also `project_id`-keyed with
  no `id` column).
- No field is required — every column is nullable or defaults to
  `'unknown'`, matching "do not make every field mandatory."

## 8. Employee handoff

**Extends `project_staff_assignments` in place — one handoff note per
assignment, not a new task-management system.** New nullable columns:

```sql
create type staff_request_type as enum (
  'estimating', 'planning', 'site_review', 'permitting', 'scheduling', 'vendor_pricing', 'other'
);
create type handoff_priority as enum ('low', 'normal', 'high', 'urgent');

alter table project_staff_assignments
  add column requested_work         staff_request_type,
  add column priority               handoff_priority not null default 'normal',
  add column target_due_date        date,
  add column next_action            text,
  add column internal_instructions  text;
```

- "Who owns each open item" is satisfied structurally: each
  `project_staff_assignments` row already has exactly one `profile_id` —
  the assigned person *is* the owner of that row's handoff note. No
  separate multi-item task table is introduced; that would be new task-
  management infrastructure the owner explicitly said not to invent.
- Writes inherit the existing `project_staff_assignments_admin_manage`
  policy automatically (new columns on an existing table, same RLS) — no
  new policy needed. This keeps handoff-note authorship where project
  creation and staffing already sit: admin-only. If the owner wants a PM to
  be able to edit their *own* handoff note text once assigned, that's a
  policy change beyond this package's scope — noted, not assumed.
- **Visibility (the actual "handoff"):** the assigned employee already sees
  the project (RLS via `project_staff_assignments`/`is_org_staff`) the
  moment they're assigned — that structural minimum already exists and
  needs no new code. This package adds a compact "Your assignment" card to
  the existing Overview screen (`AdminOverviewScreen.tsx`) for any staff
  session with an active assignment on the current project. Per the owner's
  list, the card shows all of: **what the project is**
  (`project_briefs.summary`), **their assigned function** (`staff_function`),
  and the assignment's own `requested_work`, `priority`, `target_due_date`,
  `next_action`, and `internal_instructions` — plus **what's received /
  what's missing**, drawn from the checklist's own derived-status logic
  (§9), not a separate computation. Reuses the screen every staff session
  already lands on, not a new route.
- **Deliberately not built:** any notification, email, reminder, or
  in-app alert when a handoff note is created or changed. The owner's
  "design a future notification/task handoff" instruction is honored by
  making these fields queryable now (so a future notification package has
  real data to alert on) without inventing delivery infrastructure —
  matches the Completeness Matrix's own open finding that "Notifications"
  has no owning package yet and needs an owner decision on placement,
  which this document does not attempt to resolve.

## 9. Setup checklist

Revises `ProjectSetupChecklist.tsx` (already exists, already the
post-creation landing screen) rather than replacing it. Each item's status
is **derived from real data at read time** — never a separately stored flag
that can drift out of sync — matching the existing "no screen computes its
own numbers, everything routes through a real read" discipline applied here
to checklist state instead of financial figures.

| Item | Status source | Link |
|---|---|---|
| Project identity | Always complete post-creation (name/type/number always set) | Static summary |
| Homeowners & decision-makers | Derived from `project_clients` row count / `info_status` values | **Real** — new contacts section |
| Concept & scope | Derived from `project_briefs` field completeness | **Real** — new brief section |

**This is a deliberate deviation from the owner's literal four-state list**
(Not started / In progress / Waiting on client / Complete): only three of
the four are implemented now — **Not started / In progress / Complete**,
computed from whether the underlying rows/fields exist and are filled in.
**"Waiting on client"** is not implemented as a derived state in this
package — it's a workflow signal (staff requested something and is
waiting on a response), and no request/notification infrastructure exists
yet to know objectively when that's true (see §4's explicit exclusion). A
future intake-request package can add it once that infrastructure is real,
without changing this checklist's shape.

## 10. Architecture and safety — preserved, not touched

- RLS/project isolation: every new table gets its own `is_org_staff(project_id)`-
  or `is_financial_staff`-based policy per the existing pattern; nothing here
  weakens or bypasses an existing policy.
- Admin-only project creation: unchanged — `create_project_with_defaults()`
  keeps its `is_org_admin_for_org()` check and the RLS `projects_staff_insert`
  policy stays admin-only.
- Revocable staff assignments: unchanged — new handoff columns ride on the
  existing table and existing admin-only write policy.
- Audit history: every new table gets an audit trigger — `log_audit()` for
  ordinary `id`-keyed tables, `log_audit_project_settings()` (reused) for
  the two `project_id`-keyed 1:1 tables (§5, §6).
- Existing project lifecycle (schema/017's reversible statuses): untouched.
- Existing project-number compatibility: explicitly designed for in §1 —
  old numbers untouched, new numbering coexists safely.
- Integer cents: `target_budget_low_cents`/`target_budget_high_cents` are
  `bigint`, matching every other money column in the schema.
- Existing financial ledgers: untouched; §5 explicitly reasons through why
  the preliminary budget range does not become a parallel model.
- P5 Tasks 1–6: untouched by this package; P5 Task 7 remains blocked
  pending P3 (not P3.1) acceptance, unchanged.

**Service/repository pattern (per `AI-ASSISTANT-ARCHITECTURE.md` and
`TARGET-ARCHITECTURE.md` §14):** every new mutation gets a plain service
function in `packages/02-app-shell/src/services/` (extending
`projectService.ts` or a new sibling file — decided at implementation time)
wrapped thinly by a Server Action; every new read gets a repository
function. No business logic lives in a Server Action or a React component.
This is not new policy — it is the same pattern P3 and P4 already follow,
applied to this package's new tables so a future P15 assistant call can use
the exact same functions under the exact same session, unchanged.
