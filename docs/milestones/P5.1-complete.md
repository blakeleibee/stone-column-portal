## Scope

An organization-level vendor directory closing the highest-priority gap found during P5's own live preview: no admin-side UI existed anywhere to create or manage a `vendors` row. Full design record: `docs/production-build/P5-EXTENSION-PACKAGES-DESIGN.md`, Section 5's "P5.1 — Vendor Directory & Onboarding" subsection. No implementation plan file exists for this package (unlike P4/P5's 12-task plans) — its scope was small and well-bounded enough to implement directly against the approved design, per the owner's own instruction to "identify only decisions that truly require owner input... proceed without repeating the design exercise" where the design already resolved something.

**Explicit exclusions, honored:** no outbound email, no vendor-facing login/portal, no bid-package document upload/versioning, no inbound-email correspondence (all P5.2); no material-order comments/documents (P5.3); no changes to Commitments, the budget screen, or any committed-cost display logic (P5.4); no touches to P5.0's project-context-safety code (vendors are organization-scoped, not project-scoped, so P5.0 has no bearing here).

## What shipped

- **Schema** (`schema/020_vendor_directory.sql` + down, `schema/021_vendor_directory_fixes.sql` + down — two migrations, the second a same-package follow-up rather than an edit to the first, per this repo's "never edit an already-applied migration" convention): `vendors` gains `legal_name`, `website`, `trades text[]`, `service_area`, `preferred_communication_method`, `payment_terms`, `merged_into_vendor_id` (self-FK). New tables `vendor_contacts` (contact-plus-role child table, modeled on the still-unimplemented `project_decision_makers` *design* as a pattern, not existing code), `vendor_documents` (W-9/certificate-of-insurance/license/other, with an explicit `status` enum — missing/requested/received/verified/expired/not_applicable — never inferred purely from file presence), and `vendor_document_access_log` (a new pattern for this codebase: auditing *reads*, not just writes, since the standard audit trigger only fires on mutation). A partial unique index (`vendor_contacts_one_primary_per_vendor`, added in the follow-up migration) makes "at most one active primary contact per vendor" a real database constraint, not just application-level sequencing.
- **A new RLS helper, `is_accounting_or_admin_staff_for_org()`**, mirroring `is_financial_staff()`'s existing style but organization-scoped — restricts `category='w9'` `vendor_documents` rows to admin/accounting staff specifically, while certificate-of-insurance/license rows stay on the ordinary organization-wide staff policy every other vendor table already uses. No enum change was needed: `staff_function` already had an `'accounting'` value (added in P3).
- **Service layer** (`packages/02-app-shell/src/services/vendorService.ts`): create/update/archive/reactivate a vendor; list with search/trade/active-status filters (excluding archived and merged-away vendors from selector-style results); vendor detail including contacts, documents, and a merge-aware history view; upsert/archive a vendor contact, with the designated primary contact's name/email/phone mirrored onto the vendor's own headline fields for backward compatibility with every existing reader of those columns (bid invites, material-order vendor selection) — and, after the follow-up fix, correctly cleared to `null` rather than left stale if the mirrored primary is later demoted or archived with no replacement designated; exact-normalized-match duplicate detection (case/whitespace/common-suffix-insensitive) surfaced as a dismissible warning, never a hard block; a real merge/unmerge feature that archives the "loser" without ever rewriting historical `bid_submissions`/`material_orders` rows, blocks merge chains and self-merges (enforced at both the service layer and, independently, by a database trigger), and is fully reversible; an atomic-from-the-caller's-perspective W-9 signed-download-URL function that never returns a URL without a corresponding access-log write succeeding first.
- **Storage**: `StorageAdapter`'s interface extended (backward-compatibly — confirmed the existing `/api/documents/[id]/download` route needed zero changes) to support time-limited signed URLs, required for W-9 downloads specifically. New Route Handlers under `apps/web/app/api/vendors/[vendorId]/documents/` for vendor-document upload/download, separate from the existing project-scoped `documents` table's own route (vendors aren't project-scoped).
- **UI**: a new `/admin/vendors` screen (organization-level nav entry, alongside Projects/Contacts/Settings) with a searchable/filterable list showing a computed status indicator per vendor (e.g. "W-9 missing," "COI expiring soon") — deliberately computed from real document records on every read, not a stored rollup column that could drift out of sync — and a detail view sectioned into Overview, Contacts, Compliance & Licensing, Payment Terms, Internal Notes, and History, each independently editable rather than one long form. Small "Manage Vendors" links added beside the existing vendor selectors in `BidPackageWorkspace.tsx` and `MaterialOrderWorkspace.tsx` — navigation only, no new vendor concept scoped to a project or a bid package.

## Independent review

Two review passes, both with a clean "GO" verdict:

1. **Full review of the original three commits** (schema/RLS, service+storage+UI, unit tests). Verified every claim empirically rather than on trust — read the full migration against the real schema, ran the SQL tests and then deliberately weakened the W-9 RLS policy to confirm the test suite actually catches it (it did — "non-accounting, non-admin staff cannot read a category='w9' vendor_documents row" failed as expected — then restored and reconfirmed clean), ran the unit tests directly, independently re-ran the full hosted-dev and browser verification rather than trusting the implementer's report. Found zero blocking issues; three explicitly non-blocking follow-ups (below), which the owner then asked to have fixed before merge.
2. **Focused review of the follow-up fix commit** (`77155be`) alone. Confirmed the new migration is genuinely additive (zero-diff against `schema/020_vendor_directory.sql`), confirmed both service-layer fixes correctly detect the specific condition they're meant to catch (not a broader, false-positive-prone check), reverted each fix in turn to confirm its new test actually fails without it, and independently re-verified all three fixes against real hosted dev. Also confirmed, via a service-role query across the whole hosted-dev database, that the new constraint holds against all real existing data, not just fresh test rows. Zero findings.

**Findings from the first review, fixed in `77155be` before merge (none shipped unresolved):**
1. No database-level constraint had backed "one primary contact per vendor" — enforced only by sequential application-layer writes with a narrow concurrent-race window. Fixed with a partial unique index; hosted-dev data was checked first and found to have zero existing violations, so no cleanup step was needed.
2. Demoting or archiving a vendor's current primary contact with no replacement designated left the vendor's headline `contact_name`/`email`/`phone` mirror stale rather than reflecting the new reality. Fixed: both `upsertVendorContact()` and `archiveVendorContact()` now clear the mirror to `null` in that specific case — a deliberate honest-empty-state choice over either leaving stale data or silently auto-promoting a different contact.
3. `getVendorHistory()`'s subcontract entries hardcoded `fromVendorId` to whichever vendor was being viewed, instead of resolving the real originating vendor the way every other entry type in the same function already did — harmless today (nothing rendered the field) but would have misattributed a merged-away vendor's own subcontract activity to the surviving vendor's id. Fixed by resolving the real awarded submission's vendor id through the same join pattern already used for bid-submission entries.

## Unresolved decisions

None. The merge/reconciliation strategy — the one piece of real scope not covered by the original P5-EXTENSION-PACKAGES-DESIGN.md design doc — was designed during implementation (explicit, two-step-confirmed, never rewrites history, blocks chains, fully reversible) and confirmed correct by both review passes; no open question remains.

## Known limitations

- **No fuzzy/similarity duplicate detection** — only exact-normalized-match (case/whitespace/common-suffix-insensitive). A genuinely different-looking name for the same real vendor (e.g. a DBA name vs. a legal name with no textual overlap) won't be caught. Explicitly deferred in the original design as a "reasonable future upgrade, not v1."
- **No banking/tax-ID numbers stored as structured, queryable fields anywhere** — W-9/insurance/licensing information lives only as an uploaded document plus a status/expiration date, per the owner's explicit sensitive-data boundary. Storing actual account/tax-ID numbers as real data remains a distinct, not-yet-made security decision (field-level encryption or a dedicated compliant subprocessor), unchanged from the design doc.
- **`trades` is a plain text array, not a normalized/controlled taxonomy** — a deliberate v1 simplification; a real lookup table is a reasonable future upgrade if search/filter needs demand it.
- **The "onboarding status" shown per vendor is computed live from `vendor_documents`, not a stored field** — by design, to avoid a second source of truth that could drift from reality. This means the list view's status indicator does real per-vendor computation on every read; if the vendor list ever grows very large, this may be worth revisiting for performance, but was not a concern at today's scale.
- **`OneDriveStorageAdapter` remains a stub** — vendor documents, like every other document in this codebase today, are stored via the dev-only `LocalFilesystemStorageAdapter` in the current environment; production file storage (Microsoft Graph/OneDrive) remains unimplemented, unchanged from before this package.
