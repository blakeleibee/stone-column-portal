**3. Create a test vendor and complete the full lifecycle as that vendor:**

1. As staff, go to **Vendors** (`/admin/vendors`) → "Add a vendor" → give it
   a name and a real-looking email you control the inbox naming convention
   for (e.g. `yourtest+vendor-a@example.com`) — this becomes the vendor's
   bidding email, the one address invitations and correspondence resolve to.
2. Go to **Bids** (`/admin/bids`), pick or select a project, "Create a bid
   package," fill in a cost code and title, then fill in **Package
   details** (inclusions/exclusions/alternates/allowances/pricing/schedule/
   bid instructions/Stone Column contact) and **Publish** it.
3. Upload at least one document, and try both visibility states (an
   unchecked "vendor-visible" plans document and a checked "Internal only"
   one) — confirm only the non-internal one is meant to reach the vendor.
4. Under **Vendors & submissions**, select your test vendor and click
   **Invite** — note the "Will be sent to: ..." line that appears *before*
   you click, and the resulting outcome. Since no email provider is
   configured in this environment (by design — see "Explicit constraints"
   in the governing plan), the invitation is recorded honestly as
   *pending_provider_configuration* and a one-time **access link**
   (`http://127.0.0.1:5173/vendor/invite/<token>`) is displayed for manual
   hand-off — copy it.
5. Open that access link in a private/incognito window (or a second
   browser) — this is the vendor's real first-access landing page. Fill in
   "New vendor contact?" with a full name, the SAME email the vendor record
   uses, and a password, then "Create account and continue." You land on
   the real vendor bid package view: assembly fields, the one vendor-
   visible document, and (once you use them) Q&A and addenda.
6. As the vendor: ask a question, submit a bid amount, then submit again
   with a different amount to see the full revision history preserved.
7. Back as staff: answer the question under **Questions & answers**, issue
   an addendum under **Addenda**.
8. As the vendor: acknowledge the addendum.
9. As staff: under **Correspondence**, select the vendor's thread, send a
   message (optionally attaching a file) — as the vendor, see it and reply.
   Confirm the message shows sender, recipient, timestamp, and delivery
   status.
10. To see per-vendor isolation for yourself, repeat steps 1–9 with a
    *second* vendor invited to the *same* package, then confirm from the
    staff correspondence "Thread with" dropdown that each vendor's thread
    is separate, and that switching between them never shows the other
    vendor's messages, pricing, or documents.
11. **Revoke/reactivate a vendor's access (final-review addition — this is
    the step Phase E itself flagged it could not verify through the UI):**
    under **Vendors & submissions**, each invited vendor's row now has an
    **Access** column with a **Manage** button. Click it to see that
    vendor's registered portal user(s), each with a **Revoke** or
    **Reactivate** action. Click **Revoke** on your test vendor, then open
    that vendor's own browser session and confirm it immediately loses the
    bid package (a clean "not found"-style empty state, not an error) —
    then click **Reactivate** and confirm access is restored. Note this
    button ends/restores that PERSON's access to every bid package for
    their vendor company, not just this one package — the on-screen caption
    says so.
12. To award: once a submission's status is "submitted," click **Award**
    on that row, confirm "Yes, award," then check **Commitments**
    (`/admin/commitments`) for the new committed-cost row.

## Final-review pass (whole-package audit) — findings and fixes

After Phases A–E were each independently reviewed clean, one last
independent pass reviewed the ENTIRE package as a single integrated diff —
specifically hunting for anything that only shows up when every phase is
combined, rather than re-checking each phase on its own again. Two things
came out of it:

**1. The revoke/reactivate button Phase E itself flagged.** Phase E's own
report noted it had only proven vendor revocation correct via direct
script/DB manipulation, not through the actual product UI, even though the
owner had explicitly listed "revoke/reactivate access" as something to
verify. Investigation found: P5.1's Vendor Directory "active/inactive"
toggle (`vendors.is_archived`) is a **different concept** — it archives a
vendor's directory listing and is never checked by `is_vendor_member()` or
any bid-access RLS policy, so it would **not** actually revoke bid access if
used for that purpose. The real mechanism (`vendor_members.revoked_at`, via
the already-built and already-live-checkpoint-tested `revokeVendorMember()`/
`reactivateVendorMember()` service functions and Server Actions) had no
screen wired to it at all. Fix: a small, narrowly-scoped **Vendor Access**
panel added to `BidPackageWorkspace.tsx`'s "Vendors & submissions" table
(see walkthrough step 11 above) — no new authorization logic, no schema
change, just a UI surface over capability that already existed and was
already proven correct.

**2. A real, previously-undetected security gap: revoked vendors could
silently reactivate themselves.** Reading schema/022–028's RLS policies and
`accept_vendor_bid_invitation()` together (rather than phase-by-phase) found
that revoking a vendor's `vendor_members` row never touched their original
`bid_vendor_access_invitations` token — that token stays valid (unexpired,
unrevoked) for up to 14 days after issuance. A revoked vendor who still had
their original invitation email could simply revisit that same link; the
RPC's own `ON CONFLICT ... DO UPDATE SET revoked_at = null` branch would
silently clear their revocation again, with **zero staff action**. This
became directly exploitable the moment "Revoke" became a real button (fix
#1 above), so it was fixed immediately rather than left as a flagged risk:
`schema/029_vendor_bid_invitation_replay_reactivation_fix.sql` restricts
that reactivation branch to invitations that have never been accepted
before, closing the replay path while leaving the one legitimate case (staff
issuing a genuinely new invitation to bring someone back) untouched — the
normal, intended path back from revocation is now exclusively the explicit
"Reactivate" button from fix #1. Covered by a new dedicated SQL test file
(`tests/sql/package_p5_2_final_review_replay_reactivation_fix_tests.sql`)
and re-verified against real hosted dev (see below) — pushed to hosted dev
via `supabase db push` and confirmed live, not just in the local PGlite test
harness.

**Also re-confirmed, no changes needed:**
- `award_bid()` (schema/015) has a byte-for-byte zero diff across the entire
  branch, and `budget_ledger` is referenced nowhere in any of schema/022–029
  (not even in a comment).
- Cross-org vendor identity, third-vendor (3+) scenarios, correspondence/
  document isolation, and both service-role call sites were all
  independently re-audited across every phase's RLS together and found
  sound (see the full review's report for the file/policy-level detail).

**Fresh hosted-dev spot-check** (`scripts/db/live-p5.2-finalreview-
checkpoint.mjs`, `P5.2-FINALREVIEW-`-prefixed data, no dev server required):
**39/39 checks passed**, including three (not just two) vendors invited to

completely unaffected, the replay-reactivation exploit above confirmed

## Issues found and fixed during this phase

   build directory had been overwritten by an intervening `npm run build`
   (a production build) run while `next dev` was still live, which broke
   all client-side hydration (every static JS/CSS chunk 404'd, so no
   button/form on any page actually worked in a real browser, though the
   server-rendered HTML and all API/Server-Action routes were fine). Fixed
   by stopping the dev server, deleting `apps/web/.next/`, and restarting
   `npm run dev` cleanly — no application code changed. Documented above so
   this doesn't recur during your own review.
2. No genuine application defect was found anywhere in P5.2's four phases
   during this verification pass. Two script-level test-assertion bugs in
   the new Phase E integration script itself (an inverted revision-amount
   comparison, and calling the vendor-scoped `listVendorVisibleBidQuestions`
   from a staff session instead of the staff-scoped `listBidQuestions`)
   were found and fixed before the script's own final passing run — these
   were bugs in the verification script, not in the product.

## Line-by-line: the 15 owner requirements, and how each was verified

1. **Inviting a vendor sends the bid invitation to the primary email
   stored on the canonical vendor record.** — `inviteVendor()` resolves
   `vendors.email` server-side and uses it as the sole recipient; proven
   with real data in the Phase E script (`recipientEmail === VENDOR_A_EMAIL`)
   and visually in the browser walkthrough ("Will be sent to: ...").
2. **Require a valid recipient and show exactly who will receive it
   before sending.** — A vendor with no email on file gets a warning, not a
   silent invite (Phase E script, `Vendor NoEmail` case); the UI shows
   "Will be sent to: [email]" before the Invite button is ever clicked
   (screenshot 11).
3. **Support multiple invited vendors without exposing one vendor's
   identity, pricing, files, or correspondence to another.** — Proven with
   two real vendors on the SAME package throughout Phase E's script (zero
   cross-vendor reads of documents, revisions, Q&A, or correspondence) and
   the browser walkthrough (separate threads never mixed, screenshots 35/36).
4. **Create the vendor access/membership record required by RLS before
   access is granted.** — Confirmed live: zero `vendor_members` rows exist
   before acceptance, exactly one per vendor exists immediately after
   `accept_vendor_bid_invitation()`, before any other read succeeds.
5. **Provide secure vendor access to only the bid packages they were
   invited to.** — Existing RLS (`is_vendor_member`), re-verified end-to-end
   with real sessions in the Phase E script and browser walkthrough; no
   regression.
6. **Let staff attach organized plans, specifications, scope documents,
   photos, addenda, and other reference material using the existing
   document-storage architecture.** — Real files uploaded through the same
   `LocalFilesystemStorageAdapter`/`uploadBidPackageDocument()` path the app
   itself uses, both categorized and visibility-flagged, in both the script
   and the live UI.
7. **Give vendors a clear package summary, scope, cost code/trade, due
   date, documents, addenda, questions, and submission instructions.** —
   Verified vendor-side read of every field (`getVendorVisibleBidPackage`)
   plus documents/addenda/Q&A, both via the script and visually in the
   vendor's real browser session.
8. **Allow vendors to submit and revise bids until the permitted
   deadline/state, with complete version and audit history.** — Vendor A
   submitted then revised (2 immutable `bid_submission_revisions` rows,
   oldest first, exact amounts preserved); a cancelled-package submission
   attempt is rejected (covered by the pre-existing Phase C checkpoint,
   re-confirmed unaffected).
9. **Add a private per-vendor correspondence thread on the bid page.** —
   `entity_messages` scoped by `(bid_package_id, vendor_id)`; both vendors
   have their own thread, neither can read the other's, staff can address
   either explicitly.
10. **Send staff messages by email and route valid vendor email replies
    and attachments back into the correct thread.** — A real Svix-signed
    inbound webhook POST is routed into the exact right thread
    (`status=routed`, correct `vendor_id`/`bid_package_id`/body); staff-to-
    vendor messages resolve the real recipient email honestly (no real
    provider configured in this environment, by explicit constraint —
    recorded as `pending_provider_configuration`, never falsely claimed as
    sent).
11. **Display sender, recipient, timestamp, direction, delivery status,
    and attachments.** — Confirmed on every message row in both the script
    and the live correspondence UI (screenshots 29–36), including a real
    file attachment sent and visible on the vendor's side.
12. **Keep the portal as the system of record for correspondence.** —
    Staff retains full read access to both vendors' complete threads even
    after vendor A's access was revoked (Phase E script + screenshot 39);
    nothing is ever staff-inaccessible once written.
13. **Include safe handling for duplicate webhooks, spoofed replies,
    unmatched messages, bounces, failures, and retries.** — All five
    quarantine/duplicate cases (duplicate svix-id, spoofed signature,
    unmatched token, sender mismatch, revoked vendor) return clean 200
    responses with the correct reason, never a 500, never a false route,
    proven with real signed HTTP requests against the running dev server.
14. **Preserve the rule that awarding a bid creates a commitment only
    after explicit approval; it must not overwrite the approved estimate
    or budget.** — `award_bid()` requires an explicit staff RPC call on a
    `submitted` bid; exactly one `committed_costs` row was created, and
    `budget_ledger` was queried and confirmed to have zero rows for the
    test project both before AND after the entire flow (invites,
    submissions, revisions, Q&A, addenda, correspondence, webhooks,
    revocation, and the award itself).
15. **Preserve organization/project isolation, vendor privacy, document
    permissions, audit history, and all completed P5/P5.1 behavior.** —
    Full regression suite green (typecheck/test/build); `/admin/commitments`,
    `/admin/procurement`, and `/admin/vendors` all spot-checked live and
    working; revoking vendor A's access mid-package produced immediate,
    total loss of access (package view, documents, own submission, Q&A,
    correspondence) confirmed live in vendor A's own browser, while vendor
    B was completely unaffected (confirmed live in vendor B's own browser)
    and staff retained full visibility of both, never mixed.
