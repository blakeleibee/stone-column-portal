## Scope

A schema-only package inserted between P1 (complete) and P4 (Estimating
& Budgeting UI), triggered by `docs/production-build/WORKBOOK-GAP-ANALYSIS.md`
— an approved gap analysis comparing this portal against Stone Column's
actual cost-plus Excel workbook
(`docs/reference/Stone_Column_Cost_Plus_Blank_Template.xlsx`, now
tracked in git). That analysis found the portal's cost-code model (18
broad fixture categories) was far coarser than the real business's (113
numbered codes across 7 divisions), which P4 would otherwise have built
real budget-entry UI on top of. Full scope, every design decision, and
the six deliberately-unresolved workbook naming/categorization
questions: `docs/production-build/P2.1-DESIGN.md` (authoritative — read
that file, not just this summary, before building anything on top of
this package).

**In scope:** normalized `divisions`; all 113 workbook cost codes with
activity names and two independent visibility flags
(`include_in_estimate`, `billable`, distinct from the pre-existing
`fee_eligible`); a vendor master table; organization billing identity;
client billing/contact information; project financial settings
(deposit %, estimate/invoice numbering, draw counter, estimate terms
text); an append-only credit-applied tracking ledger.

**Explicitly out of scope (unchanged, still true):** estimates, vendor
quotes, change orders, QuickBooks import wiring, draws, invoices,
invoice lines. Nothing in this package reads or writes `budget_ledger`,
`expenses`, `committed_costs`, `forecast_entries`, or `fee_ledger`. No
UI was built — this is data model and seed/import logic only.

## Independent review

A fresh-context review (no prior involvement in authoring the package)
checked RLS correctness/completeness, composite-FK cross-project
integrity, the `apply_standard_cost_code_template()` RPC's security
model (SECURITY INVOKER + RLS, not SECURITY DEFINER), `credit_ledger`'s
append-only enforcement, the 113-row seed's fidelity against a direct
independent re-parse of the actual `.xlsx` file, test-suite quality (no
vacuous assertions, every new policy has coverage), down-migration
dependency ordering, scope discipline, and the six-unresolved-decisions
claim.

**Verdict: ready to ship, no Critical or Important findings.** Two
non-blocking Minor findings were fixed before sign-off anyway:

1. A division-count typo in `WORKBOOK-GAP-ANALYSIS.md` §1 (Foundation/
   Other Project Costs counts were transposed-looking; the migration's
   actual seed data was always correct, only that one summary table was
   wrong).
2. `vendors`/`project_financial_settings` DELETE was neither audited
   nor blocked, unlike every other mutable table in this schema. Fixed:
   `vendors` now blanket-rejects DELETE (matching the
   `committed_costs`/`forecast_entries`/`budget_suggestions` "never
   deleted, only archived" precedent — it already carries
   `is_archived`); `project_financial_settings` DELETE is now audited
   but not blocked (blocking would break its `ON DELETE CASCADE` from
   `projects`).

Full review detail and rationale for both fixes:
`docs/production-build/P2.1-DESIGN.md`'s "Independent review" section.

## Unresolved decisions (flagged, not resolved — belongs to whoever owns the cost-code list)

1. `5011`/`5111`/`5170` carry an unexplained `***` marker in their
   activity names, with no legend anywhere in the workbook.
2. Inconsistent material/sub abbreviation style (`- Mat`/`- Sub` vs.
   `- M`/`- S`/`- Conc` on a cluster of codes: `5030`/`5031`/`5035`/`5036`).
3. Two "trim material" codes with an unclear boundary: `5049 Trim -
   Materials` vs. `5050 Trim -Int Doors - Mat`.
4. Possible scope overlap: `6060 Fence` (Exterior Improvements &
   Closeout) vs. `7050 "Pool, pavers, Fence"` (Other Project Costs).
5. `7050` bundles three unrelated scope items into one code, unlike
   every other single-scope code.
6. `7082`/`9999` combine `include_in_estimate = true` with `billable =
   false` — confirmed load-bearing by this package's own tests, not a
   data-entry error, but still worth a human confirming business intent.

All six are visible today by querying `cost_code_templates` directly.
None were changed by this package.

## Known limitations

- `credit_ledger` has no reversal-magnitude enforcement trigger yet
  (unlike `budget_ledger`/`fee_ledger`) — deliberately deferred until
  P6 (Billing: Draws) actually consumes this ledger; nothing reads from
  it today.
- `scripts/db/seed.mjs` does not call `apply_standard_cost_code_template()`
  as an RPC — it reproduces the function's logic directly against the
  templates via the service-role client, because the RPC is `SECURITY
  INVOKER` and requires a real `auth.uid()`, which a service-role
  client doesn't have (same limitation the script already documents for
  `bootstrap_organization()`). A real project-creation flow calling the
  RPC as an authenticated staff user is unaffected.
- `project_financial_settings` is a single mutable row per project, not
  an append-only ledger. Deliberate — nothing reads from it yet. **When
  P4/P6 build estimates/invoices, those tables must snapshot the values
  they used at creation time** — this is not automatic and is not this
  table's job to enforce.
- Migration 012's up→down→up reapply cycle was verified manually (a
  throwaway PGlite script), not wired into CI as an automated check —
  matches the existing, already-documented status of every other
  migration's down script in this repo.
