## Scope

Turns the project-creation screen from a contract-pricing form into a
project-intake/employee-handoff workflow, per the owner's explicit
framing: database-generated sequential project numbers (`SC-YYYY-###`,
atomic, never computed in the browser); pricing/fee terms made fully
optional at creation and movable to a new post-creation Contract &
Pricing Terms screen; a minimal required-field create form (name, type,
optional primary contact, location or "not established," a short
concept, optional staff); new homeowner/contact, concept & scope, and
property/site-info intake surfaces; a lightweight, explicitly
informational-only decision-maker flag on the existing `project_clients`
table (not a substitute for P7's real `project_decision_makers` model);
handoff-note fields on `project_staff_assignments`; a derived,
real-data-driven 11-item setup checklist. Then, per two further owner
requests, a full shared-design-system build-out and application-wide
visual modernization, followed by a scoped polish pass.

Full design records: `docs/production-build/P3.1-DESIGN.md` (feature
design, reviewed and revised once after an independent review caught two
factual errors before implementation), `docs/production-build/VISUAL-MODERNIZATION-PLAN.md`
(visual direction and implementation boundary).

**Explicit exclusions, honored throughout:** no `project_decision_makers`
table or real approval workflow (remains P7 scope); no document
upload/storage (remains P9, OneDrive/SharePoint per
`TARGET-ARCHITECTURE.md` §8); no notification/task-delivery
infrastructure; no real permitting workflow (remains P13); no QuickBooks
per-project connection (remains P4.4); no cost-code breakdown (remains
P4.1); no binding contract-amount/fixed-price total concept (still an
open future architecture decision); no redesign of any preview-only
screen (Action Center, Conversations, the fixture Contacts screen,
Selections, Documents/Updates, the client Schedule tab); no P5 work of
any kind was started or resumed.

## Bugs found and fixed along the way (none shipped silently)

1. Schema/018 review: a real concurrent-write race in the new
   `set_project_fee_terms()` supersede logic (two simultaneous calls
   could leave two "current" fee-rule rows) — fixed with a row lock plus
   a hard partial unique index as an independent DB-level backstop.
2. Schema/018 review: `generate_project_number()` was directly callable
   cross-tenant (an org admin could advance a *different* org's counter)
   — fixed with an org-membership gate.
3. Service-layer review: a latent bug where checklist-status vocabulary
   strings could leak into the shared stylesheet's CSS text on every
   page, including client-facing ones — caught by the pre-existing
   `render_smoke.tsx` regression test guarding against internal
   vocabulary reaching clients.
4. Staff-handoff UI build: `project_staff_assignments` had no SELECT
   policy for the assigned staff member's own row (admin-only) — the
   entire "employee sees their own handoff note" feature would have
   silently returned nothing. Fixed with schema/019's narrow self-select
   policy.
5. Live browser verification (twice): two separate real hydration-
   mismatch crashes invisible to typecheck/test/build — a nested
   `<form>` inside the create panel's own `<form>` (invalid HTML), and
   the `ProjectWorkspace` legacy wrapper's own unfixed raw `<style>` tag
   on `/admin/financials`. Both reproduced with a real headless browser,
   fixed, and re-verified with an actual before/after error-count
   comparison, not just a source-level fix.
6. Visual-modernization review: making pricing optional at creation made
   "no fee rule yet" a normal, reachable state — but the pre-existing
   `AdminFinancialsScreen`/`AdminOverviewScreen` data path (via
   `FinancialRepository.getFeeRule()`) had never been built to handle
   zero rows and would crash the app's own post-login landing screen for
   any project created the new way. Fixed by widening `getFeeRule()` to
   `FeeRule | null` and rendering an honest "Not yet determined" instead
   of a fabricated `$0` — `packages/01-financial-engine` itself was
   never touched.
7. Nine separate instances of the established raw-`<style>` hydration-
   mismatch bug class (apostrophes in `typography.fontFamily`/
   `-Display` HTML-escaped by SSR but never decoded by the browser's
   raw-text `<style>` parsing) found and fixed across `AppShell`,
   `BidPackageWorkspace`, `AdminOverviewScreen`, `ImportWizard`,
   `MappingProfileForm`, `AdminFinancialsScreen`, `BudgetTable`,
   `EstimateTable`, `ClientBudgetAndInvoicesScreen`, and
   `ProjectWorkspace` — the last one found only via live browser testing
   after the others were already believed complete.
8. Polish-pass review: `.sc-ui-tab` was missing `box-sizing: border-box`
   (anchors don't get the browser's UA-stylesheet `border-box` default
   that `<button>`s get), rendering the Projects-screen tabs at 54px
   against every other control's 44px — fixed and re-measured live.

## Known limitations / deferred (not defects — explicit scope boundaries)

- Project-list rows don't show a setup-progress indicator or per-row
  assigned-staff names — the data isn't threaded to
  `ProjectListWorkspace` yet (would require new data plumbing from
  `page.tsx`), correctly declined rather than fabricated during a
  visual-only pass. Real follow-up if wanted.
- No `Table` shared primitive exists yet — every list/table screen
  (`EstimateTable`, `BudgetTable`, the contacts list, bid
  packages/submissions) uses restyled native `<table>` markup instead.
  Flagged as a natural candidate for P9.5.
- `PHASE_LABELS` (enum → human label) is duplicated in three files
  (`AdminFinancialsScreen.tsx`, `AdminOverviewScreen.tsx`,
  `ProjectBriefWorkspace.tsx`) rather than unified into one shared
  constant — deliberate, to avoid a cross-task edit dependency while
  those files were being built by parallel agents. Worth unifying later.
- "Waiting on client" (the fourth checklist status the owner's original
  spec named) is not implemented as a derived state — no
  request/notification infrastructure exists yet to know objectively
  when it's true. Three states (Not started/In progress/Complete) ship;
  the fourth is a real, named, future-package addition.
- The `is_decision_maker` flag on `project_clients` is explicitly
  informational only and is not, and must not be treated as, an early
  implementation of P7's real `project_decision_makers`/
  `CLIENT-APPROVAL-MODEL.md` approval-authority system.
